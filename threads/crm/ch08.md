練氣中期・第八重「接外」

第二百零五天。

飛鴿驛的人來了。

是個皮膚黑、走路很急的中年人，自稱鄭驛長。他開門就把一封信摔到尹知行桌上。

「這封信，三天前由飛鴿從南郡送到總櫃。」鄭驛長說，「收信人是順發商號的張正吉。但我們飛鴿驛沒辦法直接交給張正吉本人 ── 他不在總櫃。」

尹知行翻開信。

是某個叫萬通商號的人寄給張正吉的私信。

「⋯⋯這應該你們送到順發商號去。」尹知行說。

「問題是。」鄭驛長說，「順發商號在南街第三進。我們飛鴿驛總櫃這邊不確定那個第三進是不是還住著張正吉 ── 因為他這個月好像搬了。」

尹知行翻人錄 #045 張正吉。

紀錄上：地址 = 南街第三進。

尹知行翻最近七天的事件（activity） log。

沒有「張正吉搬家」的紀錄。

尹知行問蘇行：「張正吉搬家了嗎？」

蘇行：「⋯⋯好像沒？」

尹知行回頭看鄭驛長：「我們紀錄上他還住南街第三進。」

鄭驛長嘆氣：「我們飛鴿驛這邊聽說的是他搬了。也許聽錯了。所以我來總櫃確認。」

尹知行那晚坐在長案前想。

問題：

飛鴿驛知道「客戶可能搬家了」。錄事司不知道。

兩邊的資訊不通。

每次飛鴿驛遇到「地址不確定」這種事，就要派人來總櫃當面確認。慢、貴、容易出錯。

理想狀況：

飛鴿驛只要聽說某個客戶搬了，自動通知錄事司。

錄事司收到通知 → 自動建一條事件「請確認 X 是否搬家」 → 指派給負責雜役。

也就是 ── 兩個系統「自動互通消息」。

尹知行翻《記事手冊》第八章空白頁。

尹知行對著《記事手冊》第八章開頭寫：

飛鴿驛通報桶（Inbox）

格式：
  時間：____
  客戶（人或商號）：____
  事件類型：搬家 / 改名 / 聯絡方式變 / 倒閉 / 合併 / 其他
  細節：____

收件流程：
  錄事司每天巳時開桶
  每張紙條 → 建立一條事件（類型：飛鴿通報）
  自動指派給該客戶的負責雜役
  原紙條保留三個月後焚毀

這就是 webhook ── 一方主動「推」訊息給另一方。

接收方不用每次去問 ── 訊息來了就被通知。

第二百一十天，蘇行跑來。

「尹副丞，今早桶裡有三張紙條。」

尹知行翻。

紙條一：張正吉搬到南街第七進（六月二十日）
紙條二：萬通商號改名為「萬通泰昌」（六月十八日）
紙條三：「鄭家布行」這個月起暫停營業

尹知行分別建三條事件：

A-1023 飛鴿通報：張正吉搬家 → 指派蘇行
A-1024 飛鴿通報：萬通改名 → 指派蘇行
A-1025 飛鴿通報：鄭家布行暫停 → 指派蘇行

蘇行接到三條事件。每一條他都得親自跟客戶確認，確認後更新人錄和商號錄。

尹知行特意規定：飛鴿通報的資訊不直接寫入正式紀錄。先建事件提醒人去確認，再由人確認後更新。

理由：飛鴿驛聽到的不一定準。要人去 verify。

第二百一十五天，鄭驛長又來。

「尹副丞。」鄭驛長說，「桶子用起來不錯。但有個問題。」

「⋯⋯什麼？」

「有時候我們紙條丟進去，會被你們的雜役當垃圾掃出來。」

尹知行閉了一下眼。

他想起前世。

webhook 沒設「確認回應」（acknowledgement）的後果。

對方把 webhook 推送過來，接收方沒回「我收到了」。對方不知道你有沒有收。如果半天沒回，對方可能重推。或者放棄。

尹知行增加流程：

飛鴿通報桶（升級版）

接收方流程：
  每天巳時開桶
  每張紙條：
    1. 抄寫到「飛鴿通報冊」
    2. 建立對應的事件
    3. 在原紙條角落畫一個朱紅印章「已收」
    4. 把已蓋印的紙條放回桶裡，等飛鴿驛取回確認

發送方（飛鴿驛）流程：
  每三日來總櫃取回已蓋印紙條
  確認「我寄出的每張紙條都有對應的朱印」
  沒有朱印的，重新寄一份

「朱印」= acknowledgement。

「重新寄一份」 = retry。

但是 ── 如果紙條已經被處理過了、然後被誤判沒朱印、然後又寄一份 ── 同一件事會被處理兩次。

尹知行於是加第四條：

4. 每張紙條編一個「通報號」（唯一）。
   抄寫到飛鴿通報冊之前，先查冊子有沒有這個號。有 = 重複，直接蓋印不處理。

「通報號」 = idempotency key。

不管同一張紙條送幾次，只會被處理一次。

第二百二十天，尹知行發現第二類「接外」需求。

是反過來的方向 ── 總櫃要主動推消息給其他單位。

例：D-001 完結後，錄事司要通知財房「順發商號這筆 5000 兩已結清」。

尹知行回頭看籙令 L-001：

L-001
觸發  拍（Deal）完結
動作  3 天後建一條事件「寄謝函」

他加 L-001a：

L-001a
觸發  拍完結
動作  立即建一條紙條丟到財房門口的「通報桶」
       格式：「拍 D-X 已完結，金額 Y 兩，客戶 Z」

財房有自己的通報桶（尹知行替財房在錄事司門口的對面也建了一個）。

每天財房派人來取。

從此 ── 錄事司和財房之間，再也不用人跑來跑去問「這筆結了沒」。

拍階段變化 → 自動丟紙條 → 對方取走 → 對方處理。

▼ 9/12（回覆串接，387 字）

尹知行在《記事手冊》第八章寫四條：

接外四條鐵則

一、訊息進來，要先 ack（確認回應）。不 ack 對方會重推。
二、訊息要有唯一編號（idempotency key）。即使重推，也只處理一次。
三、外面來的資料不直接寫入正式紀錄。先建事件給人 verify。
四、丟出去的訊息進對方的「通報桶」。對方什麼時候取、怎麼處理，他們的事。我們不替對方擔心。

第四條是他做了快兩百年才搞清楚的事。

前世他做的某個整合，每次推 webhook 給對方，他都要在自己這邊監控「對方有沒有收」「對方有沒有處理完」「對方處理失敗了沒」。

最後他在自己的系統裡寫了一大堆「處理對方狀態」的邏輯。

非常蠢。

「對方有沒有處理完」是對方的責任。他只負責「把訊息推出去」「對方回 ack 給我」。

接下來對方掉鏈子，是對方的事。

清楚的邊界，是雙方都能扛責的前提。

這一章你只要記得這三件事

1. CRM 不是孤島。跟 email、phone、marketing、billing、support 整合的能力，跟 CRM 本身一樣值錢。
2. Webhook（推）優於 API polling（拉）。即時、省頻寬。但要有 ack、idempotency、retry、安全。
3. 跨系統的責任邊界要清楚。我推給你 + 你回 ack = 結束。你後面怎麼處理，你的事。
