# 第 5 章　結拍

第五十五天。

陸瀚剛打開《拍錄》空白冊子，蘇行就跑進來。

「陸副丞！**順發商號要下大單**！」

「⋯⋯多大？」

「**三千兩的絲綢**！」

陸瀚抬頭。

三千兩 ── 是過去半年順發商號全部生意的二十倍。

「⋯⋯**對方什麼狀態**？」陸瀚問。

蘇行愣了一下。

「⋯⋯**什麼意思**？」

「我是說 ── **這單生意現在到哪一步了？對方確定要下嗎？已經談價了嗎？要不要立契？什麼時候交貨**？」

蘇行張了張嘴。

「⋯⋯張正吉今天派他兒子張仲安來，**說他爹想下這個單**。」

「**想下** ≠ **下了**。」陸瀚說，「**這是「探詢」階段，不是「成交」階段**。」

蘇行愣住。

陸瀚翻開《拍錄》第一頁。

---

陸瀚開始想：**一筆生意，從「想下」到「下了」，中間要走幾個階段**？

他列出來：

```
階段 1：探詢
       對方表達「我可能想買」，還沒明確要什麼、多少、何時。
       這時候要做的：搞清楚對方真實需求、預算、決策人。

階段 2：報價
       對方需求明確了，我方給出價格、規格、交期。
       這時候要做的：報得有競爭力、留議價空間。

階段 3：議價
       對方還價、要折扣、要送贈品。
       這時候要做的：守底線、靈活讓步、找替代方案。

階段 4：立契
       雙方同意條款，準備簽契約。
       這時候要做的：確認細節、防止反悔、安排履約。

階段 5：履約
       貨品交付、款項收取。
       這時候要做的：按時交貨、確認品質、收款。

階段 6：完結
       生意完成。
       這時候要做的：回顧、收集回饋、為下一單鋪路。

岔路：流失
       任何階段都可能對方退出。
       這時候要做的：記下流失原因（價格高、競品搶、時機不對）。
```

六個正常階段 + 一個岔路。

陸瀚在牆上釘了七張紙條，每張紙條代表一個階段。

「**順發商號 3000 兩絲綢**」這筆生意，**目前在第 1 階段「探詢」**。

---

陸瀚把這筆 deal 登記為 D-001：

```
編號  D-001
名稱  順發商號絲綢 3000 兩
客戶  Company #C-007 順發商號
聯絡人  Contact #045 張正吉、#047 張仲安
階段  探詢
估計成交金額  3000 兩
估計成交日期  尚未確定
建立日期  宣化二年六月二十一
最後更新  今日
```

每一筆 deal 都對應一個**階段**和一個**估計金額**。

陸瀚在《拍錄》最上方寫第一條心得：

> **「想下」跟「下了」差很多。**
>
> **要分階段管理**。

---

第五十七天，蘇行又來。

「陸副丞，**張仲安又來了**。他說他爹要的不是 3000 兩，是 **5000 兩**。但要分三次交貨。」

陸瀚翻 D-001。

「**金額更新成 5000 兩**。」陸瀚說，「**階段往前推到「報價」**。」

「⋯⋯為什麼？」

「**對方明確說『要多少、什麼條件』 = 探詢結束、進入報價**。」陸瀚說，「**今天該做的是給他一份正式報價單**。」

蘇行點頭，去找會計算價。

陸瀚在 D-001 紀錄底下加註：

```
[宣化二年六月二十三]
更新金額 3000 → 5000
階段 探詢 → 報價
理由：對方明確指定 5000 兩 + 分三次交貨
```

階段變更要**留下軌跡**。

未來如果這筆生意成了，可以回看「**從探詢到成交花了多少天、各階段花多久**」。
如果黃了，可以回看「**卡在哪個階段、為什麼**」。

---

第六十天，會計出了報價單。**5000 兩，分三次交，每次交完七日內結款**。

蘇行交給張仲安。

第六十二天，張仲安回信：「**家父說每次交完七日太短，要 30 日**。」

陸瀚把 D-001 的階段推進到「**議價**」。

加註：

```
[宣化二年六月二十六]
階段 報價 → 議價
對方要求：結款期 7 日 → 30 日
我方狀態：商議中
```

七天內陸瀚跟會計、跟總櫃管事討論了三次。最後決定：**前兩次交付 7 日結款、第三次 30 日結款**（折中方案）。

第六十九天，這個方案傳給張仲安。

第七十二天，張仲安回：「**家父同意**。」

陸瀚把 D-001 推到「**立契**」。

---

第七十六天，立契完成。

陸瀚推到「**履約**」。

第八十天，第一批 1500 兩絲綢交付。順發商號當場驗貨、當場結款。

第八十五天，第二批交付。

第九十天，第三批交付。

第一百二十天（30 日後），順發商號結清最後一筆。

陸瀚把 D-001 推到「**完結**」。

從**探詢**到**完結**，共 **65 天**。

---

那天晚上，陸瀚在《拍錄》最後一頁寫：

```
D-001 順發商號絲綢 5000 兩

階段時間表：
  探詢   2 天
  報價   3 天
  議價   10 天   ← 最長
  立契   4 天
  履約   12 天
  完結   34 天   ← 結款拖到最後

總計：65 天
```

「**議價**」和「**完結**」是最花時間的兩段。

「**議價**」花 10 天 ── 因為討論細節。
「**完結**」花 34 天 ── 因為結款期 30 日（議價談下來的條件）。

陸瀚知道：**未來和順發商號談 5000 兩等級的單，「從探詢到完結」大概需要兩個月**。

這就是這筆 deal 給未來所有 deal 的**參考數字**。

---

第一百二十五天，蘇行同時跑進三條 deal 進度通報。

陸瀚抬頭，看牆上七張階段紙條。

每個階段下面，已經有不只一筆 deal 在跑：

```
探詢：D-007、D-012、D-014
報價：D-002、D-009、D-011、D-013
議價：D-003、D-008、D-010
立契：D-004、D-006
履約：D-005
完結：D-001（已完）
流失：D-015（順發商號競爭對手吃掉了）
```

陸瀚一抬頭看牆，就知道**現在有幾筆生意正在跑、各自卡在哪**。

不用翻書、不用問人。

這就是「**漏斗圖**」（pipeline）。

從上往下看：探詢的最多、最後完結的最少。中間每一階段都有「**流失**」往岔路走。

---

第一百三十天，東家屠老闆又下到錄事司。

他這次拿了一張紙。

「陸瀚。」屠東家說，「**全商會今年下半年，預計能收多少錢**？」

陸瀚停下筆。

他想了一下。

「**翻拍錄**。」他說。

他召集三個雜役，把錄事司現在所有正在跑的 deal 列出來：

```
總共 47 筆 deal
階段分布：
  探詢 15
  報價 12
  議價 10
  立契 5
  履約 3
  完結 2（剛完）

每階段「最後能成交」的歷史比率：
  探詢 → 完結：20%
  報價 → 完結：40%
  議價 → 完結：60%
  立契 → 完結：85%
  履約 → 完結：95%

預期收款：
  15 × 20% × 平均金額（假設 800 兩） = 2400 兩
  12 × 40% × 800 = 3840 兩
  10 × 60% × 800 = 4800 兩
  5 × 85% × 800 = 3400 兩
  3 × 95% × 800 = 2280 兩
  ───────────
  共約 16720 兩
```

陸瀚把這個數字遞給屠東家。

屠東家看著數字。

「⋯⋯**這怎麼算的**？」

「**每筆 deal 在不同階段，最後成交的機率不同**。」陸瀚說，「**乘上金額和機率，就是這筆 deal 的『加權預期收入』**。把全部 deal 的加權預期加起來，就是商會的『**預期總收入**』。」

「⋯⋯」

「**這個數字會錯**。」陸瀚補了一句，「**會錯多少，看「機率估得準不準」、「金額估得準不準」**。**但是「有這個數」比「沒這個數」強一百倍**。」

屠東家沉默很久。

「⋯⋯**從今天起**。」他說，「**每月初，給我這個數字**。」

「是。」

「**還有**。」屠東家說，「**每個分舵主從現在開始，照拍錄方式管自己的生意**。**任何分舵主只要拿不出自己的拍錄漏斗，這個月不發薪**。」

---

陸瀚那晚在《記事手冊》第五章寫：

> **Deal 是 CRM 系統最值錢的 entity**。

> 因為它是「**未來收入**」的源頭。

> 每一筆 deal 都該有：階段、估計金額、估計時間、各階段的歷史轉化率。

> **「階段 × 機率 × 金額」加總 = 預期收入**。

> 這個數字會錯。**但它讓你看見「能不能達標」、「該不該推某個 deal」**。

第六章他要解決：人錄、商號錄、事錄、拍錄 ── 四本書之間，如何**互相串連**。

## 雜役筆記

*陸瀚《記事手冊》第五章開頭。*

**▍Deal / Opportunity**（生意 / 商機 / 拍）

代表「**一筆潛在或進行中的生意**」的 entity。CRM 的第四個基礎 entity，也是 **B2B 銷售場景最核心的 entity**。

一筆 deal 包含：

```
- id              主鍵
- name            生意名稱（「順發 5000 兩絲綢」）
- account_id      涉及哪家公司
- primary_contact 主要聯絡人
- stage           階段（探詢 / 報價 / 議價 / 立契 / 履約 / 完結 / 流失）
- amount          估計金額
- expected_close  預計成交日
- probability     成交機率（0-100%）
- owner_id        負責業務員
- source          來源（介紹、廣告、上門、回頭客）
- lost_reason     流失原因（如果流失）
```

**▍Pipeline（漏斗）**

陸瀚牆上七張階段紙條的真名。

一個 pipeline 是「**從第一次接觸到成交**」的所有階段。各家公司各家業界 pipeline 不同，但常見的 B2B SaaS pipeline 大致：

```
Lead → MQL → SQL → Discovery → Proposal → Negotiation → Closed Won
                                                       → Closed Lost
```

陸瀚的世界（傳統商會）：

```
探詢 → 報價 → 議價 → 立契 → 履約 → 完結
                                  → 流失
```

各家業界自訂 pipeline。共通原則：**5-7 個階段**，太少看不到瓶頸、太多每階段平均拖太久。

**▍Stage Probability（階段機率）**

每個階段「**最終成交**」的歷史機率。陸瀚算的：

```
探詢 → 完結：20%
報價 → 完結：40%
議價 → 完結：60%
立契 → 完結：85%
履約 → 完結：95%
```

這些數字**每家公司不同**。你的銷售團隊要靠**過去成交紀錄**反推自己的真實數字。

**▍Weighted Pipeline（加權漏斗）**

陸瀚給屠東家的數字：

```
預期收入 = Σ (每筆 deal 的金額 × 該階段機率)
```

實務上叫 **forecasting**（預測）。**沒有 weighted pipeline 的銷售團隊，永遠在「成交了才知道收多少」**。有了 weighted pipeline，可以「**這個月還差 5000 兩**」「該推這幾筆」「議價那筆機率高、優先盯」。

**▍Sales Velocity（銷售速度）**

另一個關鍵指標：

```
Sales Velocity = (deal 數 × 平均金額 × 成交率) / 平均銷售週期天數
```

意思：**每天能賺多少錢**。改善其中任一變數都能提高 velocity：

- 增加 deal 數 → 加大 marketing 投入
- 增加平均金額 → upsell / cross-sell
- 增加成交率 → 改善 pipeline 各階段轉化
- 縮短週期 → 流程自動化、減少卡關

**▍Lost Reason（流失原因）**

陸瀚紀錄裡的「D-015 競爭對手吃掉」。

每一筆流失的 deal 都要記**為什麼流失**：

```
- 價格太高
- 對手便宜
- 對手功能比較強
- 時機不對（客戶這季不採購）
- 找錯人（聯絡人不是決策者）
- 我方反應太慢
- 跟客戶不對盤
```

**流失原因的統計，比成交統計更值錢**。你能改善流失原因 = 提高未來成交率。

**▍Deal 跟 Activity 的關係**

一筆 deal 整個過程中會產生**多條 activity**：

- 第一次見面：activity
- 寄報價單：activity
- 對方回信：activity
- 議價討論：activity
- 簽契：activity
- 第一次交貨：activity
- 收款：activity

**所有 activity 都用 deal_id 連到這筆 deal**。回看一筆 deal 等於回看它的 activity timeline。

## 這一章你只要記得這三件事

1. **Deal 是 CRM 最值錢的 entity。** 它代表「未來收入」。
2. **每一筆 deal 要有：階段、金額、預計成交日、負責人。** 沒這四個 = 不算管理。
3. **加權漏斗（金額 × 階段機率）= 預測未來收入。** 這個數會錯，但讓你看見「能不能達標」、「該推哪一筆」。
