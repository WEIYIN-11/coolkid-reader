# 第 11 章　護密

第二百七十天，蘇行衝進錄事司。

「**陸副丞**！」蘇行說，「**裴分舵主這個月看了三百次南郡的客戶紀錄。他人在西郡**。」

陸瀚翻錄事司門口的「**翻閱簿**」（每次有人取書，要登記）。

```
裴遠（西郡分舵主）
  本月查詢：南郡 C-007 順發商號 ── 47 次
  本月查詢：南郡 C-019 北街綢緞 ── 38 次
  本月查詢：南郡 Contact #128 劉萬山 ── 26 次
  ⋯⋯
```

三百多筆。

陸瀚臉色沉了。

「**派人去西郡**。」他說，「**問裴遠為什麼**。」

---

派去的人三天後回。

「**裴分舵主說 ── 他想學南郡的成交方法**。」雜役說，「**他每天讀南郡的拍錄，是為了學習，不是要搶南郡的客戶**。」

陸瀚想了一下。

「⋯⋯**動機合理**。**但這是個問題**。」

「⋯⋯什麼意思？」

「**今天裴遠看是為了學**。」陸瀚說，「**明天另一個分舵主看，可能是為了搶**。**第三天某個雜役看，可能是為了賣給競爭對手**。」

陸瀚閉了一下眼。

「**人能不能看資料，不能靠「**他想做什麼**」決定**。」他說，「**要靠「**他**該不該**看**」**規定**。」

---

那晚陸瀚開始設計**護密**。

他先把所有「**讀寫資料的人**」分類：

```
角色一  雜役
        只能看自己親自登記過的紀錄。
        可以新建。
        不能改別人寫的。

角色二  分舵記事使
        看本分舵全部紀錄。
        可以改本分舵紀錄。
        看不到其他分舵的客戶細節（只能看「客戶編號 + 名稱」）。

角色三  分舵主
        看本分舵全部紀錄 + 全商會的「漏斗總覽」。
        看不到其他分舵的客戶細節。

角色四  總櫃錄事司丞、副丞
        看全商會所有紀錄。
        可以改。
        可以合併、可以分舵間調動。

角色五  東家、長老
        看全商會所有紀錄。
        但「敏感欄位」（家庭關係、健康狀況、私事）需要額外開鎖。

角色六  飛鴿驛、財房、貨房（外部單位）
        只能透過通報桶推訊息。
        看不到任何客戶細節。
```

六種角色。每種角色一張「**令牌**」。令牌上刻著「**這個人能看哪些、能改哪些**」。

陸瀚去找屠東家。

「**東家**。」陸瀚說，「**我要規定每個人取書要先出示令牌。看到什麼、能改什麼，照令牌定**。**裴遠這種「分舵主想看別的分舵」 ── 不行**。」

屠東家看著他。

「⋯⋯**這會擋掉「**互相學習**」的可能**。」屠東家說，「**裴遠想學南郡的本事，這是好事**。**怎麼辦**？」

陸瀚想了一下。

「**「漏斗統計」全開**。」陸瀚說，「**任何分舵主可以看其他分舵的「**幾筆 deal、各階段比率、漏斗轉化**」 ── 這些是「**統計值**」，不是「**個別客戶資料**」**。」

「⋯⋯」

「**裴遠要學「南郡為什麼成交率低」 ── 看南郡的漏斗統計就夠**。」陸瀚說，「**不需要看「**順發商號跟我們聊了什麼**」這種**個別細節**」。

屠東家點頭。

---

第二百七十五天，陸瀚加第二層防護。

不只「**誰能看哪些**」，還要「**同一筆紀錄，哪些欄位敏感**」。

例：人錄 #312 鄭三郎。

```
基本欄位（角色二以上可看）：
  姓名、慣用名、所屬商號、首次往來日期

商務欄位（角色三以上可看）：
  累計成交金額、信譽等級、慣用結算方式

敏感欄位（角色五，且需特別開鎖）：
  家庭關係、健康狀況、私下偏好、特殊備註
```

陸瀚把每個欄位標上「**等級**」。

查詢時，**系統根據查詢者的令牌，只回傳該令牌等級下能看的欄位**。

例如裴遠（角色三）查 #312 鄭三郎 ── 回傳基本 + 商務欄位，**敏感欄位**那一塊用「⚪⚪⚪」遮住。

裴遠看不到「**鄭三郎的女兒下個月要嫁人**」這種細節。

如果某天裴遠真的需要 ── **要去東家那邊申請開鎖、登記用途、留下軌跡**。

---

第二百八十天，第三個防護層 ──「**所有查詢都留痕**」。

陸瀚規定：**任何人翻書、改書、合併紀錄 ── 全部記錄在「翻閱簿」**。

```
翻閱簿格式：
  時間
  人（令牌編號）
  動作（讀 / 改 / 合 / 分）
  對象（Contact #X / Company #C-X / Deal #D-X）
  細節（讀了哪些欄位 / 改了什麼）
```

「**翻閱簿**」每月由錄事司丞抽查。

如果有人「**讀了不該讀的**」「**改了不該改的**」 ── 翻閱簿直接顯示。

陸瀚這次特別狠 ── **翻閱簿本身也是 immutable**。**寫進去不能改、不能銷毀**。

---

第二百八十五天，發生了一件事。

一個雜役被抓到 ── **偷偷讀「**北街綢緞舖**」的紀錄，後來把資料賣給競爭商會**。

陸瀚調翻閱簿。

```
[宣化二年八月十二日] 雜役 #38 趙午
  讀取：Contact #128 劉萬山（基本 + 商務 + 通籙）
  讀取：Company #C-019 北街綢緞舖（所有欄位）
  讀取：Deal #D-031 北街綢緞訂單（所有欄位）
  讀取持續：兩個時辰

[宣化二年八月十三日] 雜役 #38 趙午
  讀取：Contact #128
  讀取：D-031 ⋯⋯
```

連續七天。

陸瀚抓出查詢頻率異常的雜役，**比實際工作需要多十倍以上**。

「**異常存取偵測**」 = **anomaly detection**。

陸瀚把翻閱簿輸入到一個「**統計冊**」，看每個雜役「**每週查多少筆 / 多大範圍**」。

```
全錄事司雜役平均：每週查 25 筆。
雜役 #38 趙午：每週查 168 筆。
```

明顯異常。陸瀚提早三天就應該收到警報。

但陸瀚沒設警報。**他的損失是 ── 這個雜役賣資料賣了三個月才被抓**。

---

陸瀚那晚加最後一道防護：

```
籙令 L-047
觸發  雜役單週查詢量 > 同部門平均 × 3
動作  自動標記給錄事司丞，並暫停該雜役的「跨分舵查閱權」直到人工確認
```

「**自動偵測 + 人工確認**」 = 安全標準作法。

---

第二百九十天，東家把陸瀚叫去。

「**陸瀚**。」屠東家說，「**我要再加一條規矩**。」

「⋯⋯」

「**有些客戶不希望「**他們的紀錄存在**」**。**有的客戶離開了商會、不想再被打擾。我們該怎麼辦**？」

陸瀚想了一下。

這是他前世在歐洲合規場景做過的 ── GDPR。

「**刪除權**」（right to be forgotten）。

但 CRM 紀錄又**不能真的刪**（之前章節說過：法律證據、回滾需求、歷史可追溯）。

折衷：

```
客戶要求「不要再有我」：
  1. 標記該 contact 為「已退會員」
  2. 敏感欄位（姓名、聯絡方式、地址、特殊備註）── 「**脫敏**」（mask）：
       姓名 → 「客戶 #312」
       電話 → 「09xx-xxx-1234」
  3. 歷史 activity 和 deal 保留（涉及財務、法律），但 contact_id 改指向脫敏後的「客戶 #312」
  4. 90 天後自動執行
  5. 真正的姓名等資料封存到「**離線保險庫**」（offline vault），只在法律調閱時才能取出
```

「**保留商業紀錄、脫敏個人身分**」 ── 是合規的標準解。

陸瀚把這寫進《記事手冊》第十一章末尾：

> **「該被忘記的人，要被忘記」。**
>
> 但「**該被忘記的人之前做過的事**」 ── 在合法範圍內保留。

---

那晚陸瀚翻完整個《記事手冊》。

十一章。

從第一章「客戶是誰要寫下來」、到第十一章「該被忘記的人要被忘記」。

他突然意識到 ── 整套設計**繞了一圈**：

> 第一章規定「**全商會只能寫一份客戶資料**」 ── 是「**讓資訊集中**」。
>
> 第十一章規定「**每個人只能看自己該看的**」 ── 是「**讓存取分散**」。

集中 + 分散，**同時存在**。

這就是 CRM 安全的本質：**資料集中但存取分權**。

---

陸瀚那晚也意識到第二件事。

他穿越前那次 dedup 翻車 ── **如果當時他的系統有 audit log**，**他可以證明「自動合併是上頭逼他寫的、不是他主動做的**」。

他也許不會被開除。

至少能留下「**這不是我一個人的錯**」的證據。

翻閱簿 = 留下「**誰做了什麼**」的證據 = 保護的不只是公司，**也保護寫這個系統的人**。

---

第二百九十五天，陸瀚把《護密冊》連同六種令牌的設計呈給屠東家。

屠東家翻了大概一個時辰。

「⋯⋯**陸瀚**。」他說，「**這套東西**，**比五本書加起來還重要**。」

「⋯⋯」

「**因為沒有這套，五本書就是一個漏洞**。」屠東家說，「**寫得越全，漏得越大**。」

陸瀚點頭。

「**東家**。」陸瀚說，「**還有一件事**。」

「⋯⋯」

「**這套東西全做完，下個月起，我就準備離開錄事司了**。」

屠東家抬頭。

「⋯⋯**你要走**？」

「**不是走**。」陸瀚說，「**是換到分舵去推行**。**錄事司這套，要在五個分舵全部落地。沒有人推行不會落地**。」

屠東家想了一會。

「⋯⋯**那錄事司誰接**？」

陸瀚笑了一下。

「**蘇行**。」陸瀚說，「**他已經準備好了**。」

## 雜役筆記

*陸瀚《護密冊》三道防護層。*

**▍CRM Security（CRM 安全 / 護密）**

CRM 是公司「**客戶關係**」的所有資料 ── 漏出去 = 競爭對手立刻贏、客戶信任全毀、法律後果。

三道防護層：

```
1. Who can access what?            （誰能看什麼）
2. What about sensitive fields?    （敏感欄位特殊保護）
3. What did everyone do?           （操作軌跡留痕）
```

**▍RBAC（Role-Based Access Control，角色權限控制）**

陸瀚的「**六種令牌**」。

每個使用者分配一個或多個 role。每個 role 定義「**能看哪些、能改哪些**」。

```
SDR (業務開發)：自己的 lead、自己的 contact，能讀、能新增
AE  (業務員)：自己負責的 deal、其 contact，能讀、能改、能標完結
Manager：所有下屬的 deal，能讀，極少改
Marketing：所有 contact 的基本欄位，不能看 deal 細節
Admin：全部，能改 schema
```

業界工具都內建。**最小必要原則**：給人「**剛好夠做事**」的權限，**不要多**。

**▍ABAC（Attribute-Based Access Control）**

RBAC 之上的更細粒度版本。除了「**你是什麼角色**」，還看「**這筆資料的屬性 + 當下情境**」。

例：

```
Role: 業務員
Attribute: 這筆 deal 的 owner = 你
Context: 從公司 IP 訪問、上班時間

→ 允許讀寫
```

實作複雜但更靈活。**大公司、高合規場景常用**。

**▍Field-Level Security（欄位級安全）**

陸瀚的「**敏感欄位等級**」。

同一張紀錄，**不同欄位給不同 role 看不同東西**：

```
Contact 紀錄：
  姓名、公司、職稱 ── 所有業務員可見
  Email、電話 ── 自己負責的可見
  個人偏好、家庭狀況 ── 只有 owner + manager 可見
  健康資訊、政治偏好 ── 只有 admin 在合規授權下可見
```

Salesforce、HubSpot 都支援 field-level permission。

**▍Audit Log / Trail（操作軌跡）**

陸瀚的「**翻閱簿**」。

每一次 read / write / merge / delete 留紀錄：

```
- who（誰）
- when（何時）
- what（哪筆紀錄）
- action（讀 / 改 / 合 / 分）
- details（改了什麼欄位、從什麼變什麼）
```

要 immutable（不可竄改）+ retention（保留期限至少 7 年）。

**Audit log 不只是合規工具，也是「**保護自己**」的證據**。

**▍Anomaly Detection（異常偵測）**

陸瀚捉到趙午的那條籙令。

監控每個使用者的「**正常基準**」（baseline），偏離太多 → 警報。

常見訊號：

- 短時間內大量下載資料
- 跨部門/跨權限查詢量爆增
- 非上班時間的密集存取
- 從陌生地點/裝置登入

工具：Salesforce Shield、HubSpot 內建、第三方如 Varonis。

**▍PII Handling（個資處理）**

PII = Personally Identifiable Information。

CRM 場景的 PII：姓名、Email、電話、地址、身分證號、生日。

處理原則：

1. **加密儲存**：欄位級加密（encryption at rest）
2. **傳輸加密**：TLS 1.2+ 全程
3. **存取記錄**：誰看過 PII 都留 audit
4. **最小化原則**：能不存就不存（你真的需要客戶生日嗎？）
5. **去識別化**（de-identification）：分析報表時用 hashed ID，不用真姓名

**▍GDPR / 個資法 / Right to be Forgotten**

陸瀚最後一條規矩。

歐盟 GDPR、台灣個資法、加州 CCPA 都規定：客戶可以要求「**從你系統裡刪除我的個人資料**」。

但 CRM 紀錄不能真刪（合規矛盾）。**標準解**：

```
1. 識別個人身分的欄位 → 脫敏（mask）
2. 商業紀錄（交易、發票、合約）保留，但綁定到脫敏 ID
3. 真實資料封存到 offline cold storage
4. 在法律允許範圍內、必要時才能取出
```

實作工具：OneTrust、TrustArc、Privacera。

**▍最重要的一句**

> 資料**集中**儲存，存取**分散**控管。

> 一個沒有 audit log 的 CRM = 漏洞。

> 一個沒有 RBAC 的 CRM = 災難。

## 這一章你只要記得這三件事

1. **資料集中、存取分權。** 這是 CRM 安全的核心矛盾解。
2. **三層防護：RBAC（誰能看什麼）+ Field-level Security（敏感欄位特殊保護）+ Audit Log（操作留痕）**。缺一不可。
3. **異常偵測 + Right to be Forgotten 是必要的。** 前者抓內賊、後者守合規。沒做的 CRM = 等出事。

下一章：陸瀚要離開錄事司去推全商會。但分舵主嫌「**這套太麻煩**」、雜役說「**腦袋裡記比較快**」。系統建好不代表會被用。**開市**。
