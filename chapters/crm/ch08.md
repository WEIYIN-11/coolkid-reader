# 第 8 章　接外

> *練氣中期・第八重「接外」*

第二百零五天。

飛鴿驛的人來了。

是個皮膚黑、走路很急的中年人，自稱**鄭驛長**。他開門就把一封信摔到尹知行桌上。

「**這封信，三天前由飛鴿從南郡送到總櫃**。」鄭驛長說，「**收信人是順發商號的張正吉**。**但我們飛鴿驛沒辦法直接交給張正吉本人 ── 他不在總櫃**。」

尹知行翻開信。

是某個叫**萬通商號**的人寄給張正吉的私信。

「⋯⋯**這應該你們送到順發商號去**。」尹知行說。

「**問題是**。」鄭驛長說，「**順發商號在南街第三進。我們飛鴿驛總櫃這邊不確定那個第三進是不是還住著張正吉 ── 因為他這個月好像搬了**。」

尹知行翻人錄 #045 張正吉。

紀錄上：**地址 = 南街第三進**。

尹知行翻最近七天的 事件（activity） log。

沒有「張正吉搬家」的紀錄。

尹知行問蘇行：「**張正吉搬家了嗎**？」

蘇行：「⋯⋯**好像沒**？」

尹知行回頭看鄭驛長：「**我們紀錄上他還住南街第三進**。」

鄭驛長嘆氣：「**我們飛鴿驛這邊聽說的是他搬了。也許聽錯了**。**所以我來總櫃確認**。」

---

尹知行那晚坐在長案前想。

問題：

**飛鴿驛知道「客戶可能搬家了」。錄事司不知道**。

兩邊的資訊**不通**。

每次飛鴿驛遇到「**地址不確定**」這種事，就要派人來總櫃當面確認。**慢、貴、容易出錯**。

理想狀況：

> 飛鴿驛只要聽說某個客戶搬了，**自動通知錄事司**。
>
> 錄事司收到通知 → 自動建一條 事件「**請確認 X 是否搬家**」 → 指派給負責雜役。

也就是 ── **兩個系統「自動互通消息」**。

尹知行翻《記事手冊》第八章空白頁。

---

尹知行跟鄭驛長談了第二天。

「**鄭驛長**。」尹知行說，「**我提一個方案**。**飛鴿驛每次聽到「客戶搬家、商號改名、聯絡方式變」這類事，派人來總櫃留一張小紙條。我這邊有個專門收紙條的桶**。」

「⋯⋯**只是留紙條**？**不用親自報**？」

「**對**。」尹知行說，「**紙條丟桶裡就好。我這邊每天巳時派人開桶、把紙條變成 事件、自動指派**。」

「⋯⋯」

「**省你們的人力**。」尹知行說，「**而且不漏**。」

鄭驛長想了一下。

「⋯⋯**桶在哪**？」

「**錄事司門口左邊第三根柱子下面**。」尹知行說，「**我會在桶旁邊放一疊空白小紙條，標準格式**。你們填好丟進去就行。」

鄭驛長點頭走了。

---

尹知行對著《記事手冊》第八章開頭寫：

```
飛鴿驛通報桶（Inbox）

格式：
  時間：____
  客戶（人或商號）：____
  事件類型：搬家 / 改名 / 聯絡方式變 / 倒閉 / 合併 / 其他
  細節：____

收件流程：
  錄事司每天巳時開桶
  每張紙條 → 建立一條 事件（類型：飛鴿通報）
  自動指派給該客戶的負責雜役
  原紙條保留三個月後焚毀
```

這就是 **webhook** ── 一方主動「**推**」訊息給另一方。

接收方不用每次去問 ── **訊息來了就被通知**。

---

第二百一十天，蘇行跑來。

「尹副丞，**今早桶裡有三張紙條**。」

尹知行翻。

```
紙條一：張正吉搬到南街第七進（六月二十日）
紙條二：萬通商號改名為「萬通泰昌」（六月十八日）
紙條三：「鄭家布行」這個月起暫停營業
```

尹知行分別建三條 事件：

```
A-1023 飛鴿通報：張正吉搬家 → 指派蘇行
A-1024 飛鴿通報：萬通改名 → 指派蘇行
A-1025 飛鴿通報：鄭家布行暫停 → 指派蘇行
```

蘇行接到三條 事件。**每一條他都得親自跟客戶確認**，確認後更新人錄和商號錄。

尹知行特意規定：**飛鴿通報的資訊不直接寫入正式紀錄**。**先建 事件 提醒人去確認，再由人確認後更新**。

理由：飛鴿驛聽到的不一定準。要人去 verify。

---

第二百一十五天，鄭驛長又來。

「**尹副丞**。」鄭驛長說，「**桶子用起來不錯。但有個問題**。」

「⋯⋯什麼？」

「**有時候我們紙條丟進去，會被你們的雜役當垃圾掃出來**。」

尹知行閉了一下眼。

他想起前世。

webhook 沒設「**確認回應**」（acknowledgement）的後果。

對方把 webhook 推送過來，**接收方沒回「我收到了」**。對方不知道你有沒有收。如果半天沒回，對方可能**重推**。或者放棄。

尹知行增加流程：

```
飛鴿通報桶（升級版）

接收方流程：
  每天巳時開桶
  每張紙條：
    1. 抄寫到「飛鴿通報冊」
    2. 建立對應的 事件
    3. 在原紙條角落畫一個朱紅印章「已收」
    4. 把已蓋印的紙條放回桶裡，等飛鴿驛取回確認

發送方（飛鴿驛）流程：
  每三日來總櫃取回已蓋印紙條
  確認「我寄出的每張紙條都有對應的朱印」
  沒有朱印的，重新寄一份
```

「**朱印**」= **acknowledgement**。

「**重新寄一份**」 = **retry**。

但是 ── 如果紙條已經被處理過了、然後被誤判沒朱印、然後又寄一份 ── **同一件事會被處理兩次**。

尹知行於是加第四條：

```
4. 每張紙條編一個「通報號」（唯一）。
   抄寫到飛鴿通報冊之前，先查冊子有沒有這個號。有 = 重複，直接蓋印不處理。
```

「**通報號**」 = **idempotency key**。

不管同一張紙條送幾次，**只會被處理一次**。

---

第二百二十天，尹知行發現第二類「**接外**」需求。

是反過來的方向 ── 總櫃要**主動推**消息給其他單位。

例：D-001 完結後，錄事司要通知**財房**「**順發商號這筆 5000 兩已結清**」。

尹知行回頭看籙令 L-001：

```
L-001
觸發  拍（Deal） 完結
動作  3 天後建一條 事件「寄謝函」
```

他加 L-001a：

```
L-001a
觸發  拍 完結
動作  立即建一條紙條丟到財房門口的「通報桶」
       格式：「拍 D-X 已完結，金額 Y 兩，客戶 Z」
```

財房有自己的通報桶（尹知行替財房在錄事司門口的對面也建了一個）。

每天**財房派人來取**。

從此 ── **錄事司和財房之間，再也不用人跑來跑去問「這筆結了沒」**。

拍 階段變化 → 自動丟紙條 → 對方取走 → 對方處理。

---

尹知行在《記事手冊》第八章寫四條：

```
接外四條鐵則

一、訊息進來，要先 ack（確認回應）。不 ack 對方會重推。
二、訊息要有唯一編號（idempotency key）。即使重推，也只處理一次。
三、外面來的資料不直接寫入正式紀錄。先建 事件 給人 verify。
四、丟出去的訊息進對方的「通報桶」。對方什麼時候取、怎麼處理，他們的事。我們不替對方擔心。
```

第四條是他做了快兩百年才搞清楚的事。

前世他做的某個整合，每次推 webhook 給對方，**他都要在自己這邊監控「**對方有沒有收**」「**對方有沒有處理完**」「**對方處理失敗了沒**」**。

最後他在自己的系統裡寫了一大堆「**處理對方狀態**」的邏輯。

非常蠢。

「**對方有沒有處理完**」是**對方的責任**。他只負責「**把訊息推出去**」「**對方回 ack 給我**」。

接下來對方掉鏈子，是對方的事。

清楚的邊界，是雙方都能扛責的前提。

---

第二百三十天，東家又下來。

「**尹知行**。」屠東家說，「**飛鴿驛、財房、貨房，現在都跟錄事司通報桶連起來了**。」

「⋯⋯是。」

「**全商會的「事」現在連在一起了**。」屠東家說，「**這個變化，比我自己想得還大**。」

尹知行點頭。

「⋯⋯**有個壞消息**。」屠東家說，「**今天我看南郡和北郡的拍錄漏斗，發現「順發商號」在兩邊都有獨立紀錄。**還記得我上個月問你的事嗎？**」

尹知行閉了一下眼。

「⋯⋯**記得**。」

那個問題他到現在還沒解決：**同一個客戶在不同分舵有不同編號**。

尹知行自己穿越前 ── **死在 去重（dedup） 上**。

這個世界要繞回來找他 ── **去重 是逃不掉的**。

「⋯⋯**下個月**。」尹知行說，「**我處理**。」

屠東家點頭走了。



---

那夜尹知行在牆前盤膝坐下、閉目。

這一張新貼的紙條化作微光、沉入丹田。

胸口熱了一下、又涼了一下。

自此尹知行修為 ── **練氣中期・第八重「接外」**。

## 雜役筆記

*尹知行《記事手冊》第八章 ── 「接外四條鐵則」。*

**▍Integration（整合）**

CRM 不是孤島。**它跟其他系統「互通消息」**的能力，跟 CRM 本身一樣值錢。

常見要整合的系統：

- *Email / Calendar*（Gmail、Outlook）→ 自動建 activity
- *Phone / Call*（Aircall、Twilio）→ 自動建通話紀錄
- *Marketing*（HubSpot、Mailchimp）→ 互通 contact、活動參與紀錄
- *Support*（Zendesk、Intercom）→ 客訴紀錄、health score
- *Billing*（Stripe、Recurly）→ 訂閱狀態、金流
- *Data Warehouse*（Snowflake、BigQuery）→ 分析
- *Slack / Teams*（通知）

**▍API**（Application Programming Interface）

「**主動拉**」訊息的方式。CRM 提供 API，外面系統呼叫「給我所有上週新建的 contact」。

```http
GET /api/contacts?created_after=2026-05-25
Authorization: Bearer xxx
```

API 是**被動**的。你不問，CRM 不會主動推。

**▍Webhook**

「**主動推**」訊息的方式。尹知行的「**通報桶**」就是這個。

外面系統在 CRM 註冊一個 URL。CRM 發生事件時，**主動 POST 到那個 URL**。

```http
POST https://other-system.com/webhook
Content-Type: application/json
{
  "event": "deal.closed",
  "deal_id": "D-001",
  "amount": 5000
}
```

API 是「**問才有**」、Webhook 是「**事情發生就推**」。

**▍Polling vs Push**

| 方式 | 例子 | 適合 |
|---|---|---|
| **Polling（拉）** | 每 5 分鐘呼叫一次 API 看有沒有新資料 | 來源系統不支援 webhook、可容忍延遲 |
| **Push（推 / webhook）** | 事件發生立即被通知 | 即時性、節省頻寬 |

實務上**首選 webhook**。Polling 是 fallback。

**▍Acknowledgement（ack / 確認）**

尹知行的「**朱紅印章**」。

接收方收到 webhook 後**回應 HTTP 200**。發送方看到 200 才知道「成功了」。

如果發送方沒收到 ack（接收方掛了、網路斷了、接收方回 5xx）→ **重推**（retry）。

**▍Idempotency Key（冪等鍵）**

尹知行的「**通報號**」。

接收方重複收到同一個事件時（因為重推），**用 idempotency key 去重，只處理一次**。

```python
def handle_webhook(event):
    if already_processed(event.id):
        return 200  # ack 但不重複處理
    process(event)
    mark_processed(event.id)
    return 200
```

**沒有 idempotency = 重推會造成重複處理 = 客戶被多扣一次錢、信被多寄一封**。

**▍Retry Policy（重試策略）**

發送方推 webhook 失敗了，**怎麼重推**？

常見：**Exponential Backoff**（指數退避）：

```
第 1 次失敗 → 等 1 秒
第 2 次失敗 → 等 2 秒
第 3 次失敗 → 等 4 秒
第 4 次失敗 → 等 8 秒
...
第 N 次失敗 → 放棄（dead letter queue）
```

避免「**對方掛了，發送方瘋狂重推把對方推爆**」。

**▍Webhook 的安全**

webhook 的 URL 對外公開 → 任何人都能假冒 webhook 推假訊息進來。對策：

- **HMAC Signature**：發送方用密鑰簽名，接收方驗簽
- **IP Whitelist**：只接受特定 IP 來的請求
- **Bearer Token**：HTTP header 帶 token

**▍跟外面系統的責任邊界**

尹知行第四條鐵則。

**「我把訊息推出去，對方有沒有處理是對方的事**」。

不要在自己的系統裡寫「**追蹤對方有沒有處理完**」的邏輯。對方該追蹤對方的狀態。

雙方各自擁有自己的責任邊界 = 系統可以維護。
混在一起 = 永遠不知道哪邊的 bug。

## 這一章你只要記得這三件事

1. **CRM 不是孤島。** 跟 email、phone、marketing、billing、support 整合的能力，跟 CRM 本身一樣值錢。
2. **Webhook（推）優於 API polling（拉）。** 即時、省頻寬。但要有 ack、idempotency、retry、安全。
3. **跨系統的責任邊界要清楚。** 我推給你 + 你回 ack = 結束。你後面怎麼處理，你的事。
