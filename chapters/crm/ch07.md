# 第 7 章　籙令

第一百六十天。

陸瀚的桌上每天堆四十條 activity、十二條 deal 更新、五條通籙變更。

他發現一件糟糕的事：

**順發商號的 D-001 完結之後，他規定的「三日內寄謝函」沒人寄**。

不是雜役偷懶。

是雜役**不知道要寄**。

D-001 在拍錄上推進到「完結」 ── 但「完結之後三日內寄謝函」這條規則，**寫在《記事手冊》第五章某個角落**。沒人會每天翻手冊。

陸瀚自己也忘了。

---

那天順發商號的張仲安來探。

「⋯⋯**陸副丞**。」張仲安說，「**我爹說，**上次那筆 5000 兩的單**，你們連封感謝信都沒寄**。」

陸瀚愣了一下。

「⋯⋯**對不起，我們疏忽了**。」

「**沒事**。」張仲安說，「**我們不在意一封信。我們在意的是 ── 你們連這種事都會忘**。」

說完轉身就走。

陸瀚站在原地。

他知道 ── 他**錯**了。

不是規則錯。

是「**規則靠人記**」這件事錯了。

---

那晚陸瀚坐在長案前。

他想：**規則該由「東西」記，不該由「人」記**。

什麼東西能記？

他想了三個晚上。

最後他在牆上貼第六張紙條：

> **籙令**

> 「**當 X 發生，自動做 Y**」的小冊子。

> **每一條都該寫得能讓白癡照做**。

---

陸瀚的設計：

每一條籙令長這樣：

```
編號  L-001
觸發  Deal 階段變更為「完結」
條件  完結金額 > 100 兩
延遲  3 天
動作  建立一條 Activity（類型：寄謝函，主旨：「感謝 [客戶名] 此次合作」）
負責  自動指派給該 deal 的負責人
```

四個要素：

1. **觸發**（trigger）：什麼事件發生
2. **條件**（condition）：在什麼情況下才執行
3. **延遲**（delay）：什麼時候執行
4. **動作**（action）：做什麼

陸瀚把這條規則寫進**籙令冊**。

從這一條規則寫進去之後：

每當有 deal 階段變成「完結」、金額 > 100 兩，**三天後系統自動建立一條 activity，主旨「感謝 X 此次合作」**，並指派給負責雜役。

雜役早晨翻自己的待辦事項（事錄裡 `due_at = 今天` 的條目），看到「寄謝函」，**就去寄**。

不需要記憶。
不需要翻手冊。
不會漏。

---

第一百六十五天，陸瀚加第二條籙令：

```
L-002
觸發  Deal 階段在「議價」超過 14 天沒推進
條件  （無）
動作  建立一條 Activity 提醒負責雜役：「D-X 議價卡 14 天，建議今日推進」
```

「**卡在某階段太久 → 自動提醒**」。

這條解決的是「**deal 死在中間沒人理**」的問題。

第一百七十天，陸瀚加第三條：

```
L-003
觸發  Activity 類型 = 「客訴」
條件  涉及金額 > 500 兩
動作  立即指派給東家的代書（最高層級處理）
```

「**重要客訴自動上呈**」。

第三、四條陸續加：

```
L-004
觸發  Contact 90 日內無任何 activity
條件  曾為已成交客戶（過去 deal 有 closed）
動作  建立 activity「90 日未聯絡客戶 X，建議回訪」

L-005
觸發  Deal 預計成交日已過，仍在進行中
條件  （無）
動作  提醒負責雜役更新預計成交日
```

每一條都解決一個「**靠人記會忘**」的問題。

---

第一百八十天，陸瀚回頭看籙令冊。

已經有 22 條籙令。

他發現一件事 ── **籙令彼此會打架**。

例：

```
L-002：議價超過 14 天 → 提醒
L-006（新加）：議價超過 7 天 → 提醒
```

同一個事件，**兩條籙令同時觸發**，會給雜役**兩條重複的提醒**。

陸瀚停下筆。

他想起前世。

他做的某個 CRM 系統，**workflow 規則有 300 條**。誰加的、誰改的、誰會被觸發 ── 沒人說得清。

最後維護那個系統的工程師說一句話：「**這已經不是 CRM，是寫了 300 條 if-else 的災難**。」

陸瀚不想走到那一步。

---

他在籙令冊封面寫四條紀律：

```
籙令紀律

一、每加一條，要先檢查現有籙令有沒有重複/衝突。
二、每條籙令有「最後檢查日期」。半年沒檢查的，當不再用，下架。
三、籙令觸發頻率每月統計。從沒被觸發過的 = 條件寫錯，下架。
四、籙令只做「機械性、白癡都能做」的事。任何需要判斷的，提醒人去做，不要自動完成。
```

第四條是他自己的傷痕。

他穿越前那條 dedup 邏輯，**就是讓系統自動做了「需要判斷」的事**。

「兩筆客戶該不該合併」這件事 ── **不是規則能定的**。它需要看「**這是兩個人，還是同一個人**」、看「**自然人 vs 法人**」、看「**意圖**」。

這種判斷**該交給人**。

系統做的，**只有「提醒人去做」**。

---

第一百九十天，陸瀚加第二十三條籙令：

```
L-023
觸發  新建一筆 Contact
條件  該 contact 的 email/phone 在過去 contact 裡有完全相同的
動作  建立一條 activity 給負責雜役：「新建的 contact X 跟既有 contact Y 可能是同一個人，請人工判斷」
不自動合併
```

這條規則的核心 ── 「**不自動合併**」。

陸瀚的穿越前 dedup 邏輯，自動合併了。死掉。

這個世界他規定 ── **系統只提醒，人工判斷**。

---

第一百九十五天，蘇行跑來。

「陸副丞，L-002 又觸發了。D-008 議價卡 14 天。」

陸瀚翻 D-008。

是西郡裴遠負責的一筆生意。客戶是「**萬通商號**」、金額 2000 兩、卡在議價。

陸瀚加註：「**通知裴遠**」。

蘇行帶話去西郡。

七天後裴遠回信：「**D-008 已推進到立契**。**對方議價條件最後一輪我們同意了**。**沒有籙令這條，我可能就拖到忘記**。」

陸瀚看到信，笑了一下。

---

第二百天，陸瀚在《記事手冊》第七章寫：

```
籙令的本質：

把「人會忘的規則」變成「不會忘的東西」。

但記得 ── 籙令只做兩件事：
  一、提醒人做事
  二、自動做「絕對不會出錯的瑣碎事」（例如寄一封制式信、建一條 activity 條目）

從來不做需要「判斷」的事。
判斷永遠是人的事。
```

---

那晚屠東家又下來。

「陸瀚。」他說，「**錄事司這個月少了三個雜役**。」

陸瀚抬頭。

「⋯⋯**怎麼了**？」

「**沒事**。」屠東家說，「**他們被升到分舵當記事使了**。」

「⋯⋯」

「**你那些籙令**。」屠東家說，「**做完之後**，**錄事司的人少很多事**。**所以他們有時間去學別的、被升上去**。**這是好事**。」

陸瀚點頭。

「⋯⋯**還有件事**。」屠東家說，「**最近隔壁的「飛鴿驛」想跟我們合作**。**他們的快訊每天進來，我希望「**飛鴿驛收到一封信，自動進我們的事錄**」**。」

「⋯⋯」

「**做得到嗎**？」

陸瀚想了一下。

「**做得到**。」他說，「**但這不是籙令**。**這是「跟外面系統接起來」**。**下一章**。」

## 雜役筆記

*陸瀚《記事手冊》第七章，「籙令冊封面」的四條紀律。*

**▍Workflow Automation（工作流自動化）/ 籙令**

「**當 X 發生，自動做 Y**」的規則集合。CRM 系統的「自動化引擎」。

每條 workflow 規則的四要素：

```
- Trigger（觸發事件）：什麼動作或狀態變化觸發
- Condition（條件）：在什麼情況下才執行
- Delay（延遲）：立即還是稍後
- Action（動作）：執行什麼
```

**▍常見的 Trigger 類型**

```
- Record Created（新建紀錄）
- Record Updated（紀錄欄位變更）
- Field Changed To（欄位變成特定值，例如 deal stage 變成 "Closed Won"）
- Time-based（基於時間：「過 30 天」、「每月 1 號」）
- External Event（外部事件：email 寄達、form 提交）
```

**▍常見的 Action 類型**

```
- Create Record（新建一條 activity / task / deal）
- Update Field（改一個欄位）
- Send Email / Notification
- Assign To（指派給某人）
- Trigger Webhook（呼叫外部系統，下一章）
- Add to List / Segment
- Calculate Score（更新 lead score、health score）
```

**▍實作工具**

| 工具 | 用法 |
|---|---|
| *HubSpot Workflows* | UI 拖拉、直接內建 |
| *Salesforce Flow* | 強大但學習曲線陡 |
| *Pipedrive Automations* | 簡單明瞭，適合中小團隊 |
| *Zapier / Make / n8n* | 跨工具自動化，不限 CRM |
| *自己刻*：BullMQ / Sidekiq / Temporal | 大規模、客製化 |

**▍核心紀律（陸瀚的四條）**

1. **加新規則前先檢查重複/衝突**
2. **半年沒用過的規則下架**（accumulated cruft 是 workflow 系統的死法）
3. **從沒觸發過的條件下架**（條件寫錯，永遠不會 match）
4. **只做機械性的事，需要判斷的事提醒人去做**（陸瀚穿越前死在這點）

**▍最危險的反面教材**

```
規則 #287：當 contact 的 email 在過去 contact 出現過 → 自動合併
```

**陸瀚穿越前死在這條規則**。

正確版本：

```
規則 #287：當 contact 的 email 在過去 contact 出現過
→ 標記為「可能重複」
→ 建立一條 activity 給負責人：「請人工確認 X 是否與 Y 為同一人」
→ 不自動合併
```

**▍Notification Fatigue（提醒疲勞）**

太多 workflow 提醒，使用者會麻木。最後變成全部忽略。

對策：

- *優先級*：嚴重的紅、中等的黃、輕度的灰
- *彙整*：每天早上一次「今日 X 件待處理」，不是每件事各推一次
- *Snooze*：使用者可以「等我下週再說」
- *自動消除*：條件不成立時，提醒自動消失

**▍Workflow vs Code 的界線**

簡單規則用 workflow UI 設定。**複雜規則寫程式**。

界線：

| 需求 | 用 |
|---|---|
| **條件 ≤ 3 個 boolean** | Workflow UI |
| **動作 ≤ 5 步** | Workflow UI |
| **需要呼叫外部 API、複雜計算、整合多個資料源** | 寫程式 |
| **業務邏輯穩定** | Workflow UI |
| **業務邏輯每週改** | 寫程式 + version control |

太多 workflow 規則塞在 UI 裡 → 變成「**黑魔法**」、沒人敢碰。**該寫成程式就寫成程式**。

## 這一章你只要記得這三件事

1. **規則不該靠人記。** 寫成 workflow（陸瀚的籙令）讓系統提醒、執行。
2. **Workflow 只做機械性的事，需要判斷的事交給人。** 自動合併 contact、自動回信、自動關 deal 都是大坑。
3. **Workflow 系統會累積垃圾。** 沒人維護的舊規則、從沒觸發過的條件、半年沒人改的 ── 半年清一次。
