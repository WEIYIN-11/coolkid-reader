# 第 9 章　重契

> *練氣中期・第九重「重契」*

第二百三十一天，尹知行開始面對他穿越前死掉的事。

他把南郡和北郡兩邊送回來的人錄、商號錄並排攤在桌上。

**南郡**：
```
C-007 順發商號 ── 賣鹽 ── 住南街第三進 ── 當家：張正吉
C-018 萬通商號 ── 多元 ── 住中街   ── 當家：鄭三郎
C-039 鄭家布行 ── 賣布 ── 住東街   ── 當家：鄭三郎
```

**北郡**：
```
C-103 順發商號 ── 賣鹽 ── 住南街七進 ── 當家：張正吉
C-127 萬通商號 ── 賣茶 ── 住中街   ── 當家：鄭三郎
C-145 萬通泰昌 ── 不明 ── 不明      ── 當家：鄭三郎
```

尹知行對著兩張表，看了很久。

問題不只是「**同一個商號在兩邊有兩個編號**」。

問題是 ── **同一個商號在兩邊的「資料還對不上**」。

南郡的順發商號住南街第三進。北郡的住南街七進。**尹知行知道張正吉前陣子搬家了** ── **南郡資料是舊的，北郡資料是新的**。

南郡的萬通是「多元」。北郡的萬通是「賣茶」。**尹知行猜：兩邊看到萬通的不同產品，各自寫了不一樣的「主營業務」**。

北郡有「**萬通泰昌**」 ── 這是尹知行上一章從飛鴿驛知道「**萬通改名為萬通泰昌**」的證據。北郡記了新名，南郡還沒。

三家商號。十條紀錄。**真實世界裡其實是三家**。

要把它們**合**回三家。

---

尹知行這次不會犯穿越前的錯。

他先做一件事 ── **不立刻合任何東西**。

他把這個動作叫「**重契**」。

重契分四步：

```
步驟一：標記「可能重複」
步驟二：人工判斷是否真的同一筆
步驟三：選一筆當「主筆」（master record）
步驟四：合併剩餘紀錄到主筆，但保留來源軌跡
```

**沒有任何一步是自動的**。

每一步都有**人**參與。

---

尹知行開始**步驟一：標記**。

他列「**可能重複**」的判斷規則：

```
規則 A：商號名完全相同
  → 順發商號 vs 順發商號 ✓
  → 萬通商號 vs 萬通泰昌 ✗（名字不同）

規則 B：商號名相似（去除地名、行業字、後綴詞之後相同）
  → 萬通商號 vs 萬通泰昌 → 都去掉「商號/泰昌」 → 萬通 vs 萬通 ✓
  → 鄭家布行 vs 鄭家綢緞舖 → 都去掉「布行/綢緞舖」 → 鄭家 vs 鄭家 ✓

規則 C：當家名稱完全相同
  → 兩家商號當家都是「張正吉」→ ✓
  → 兩家當家都是「鄭三郎」→ ✓

規則 D：地址完全相同
  → 「南街第三進」 vs 「南街第三進」 → ✓

規則 E：三個欄位以上完全相同
  → 強烈疑似重複
```

尹知行跑完五條規則，把所有「**可能重複**」的組合列出來：

```
組 1：C-007 順發 + C-103 順發
      （名相同、當家相同、地址不同 ── 可能搬家）

組 2：C-018 萬通 + C-127 萬通 + C-145 萬通泰昌
      （名相似、當家相同、地址不同）

組 3：C-039 鄭家布行 ── 沒組
      （北郡沒有鄭家布行，但 C-127 萬通是賣茶的 ──
       要看是不是這家被併進萬通了？）
```

組 3 是陷阱。

**鄭家布行可能完全是另外一家**。
**也可能它跟萬通有合併關係，但合併之後叫「萬通泰昌」**。

尹知行不知道。

「**不知道**」 = **不合**。

他在組 3 旁邊註：「**狀態：不確定，待調查**」。

---

尹知行做完**步驟二：人工判斷**。

他派蘇行去查兩件事：

第一，順發商號 ── **是不是同一家**？
第二，萬通商號 vs 萬通泰昌 ── **是同一家改名，還是分立**？

蘇行去了五天。回來報告：

```
組 1：順發商號 ── 確認同一家。
  證據：南郡的張正吉 = 北郡的張正吉 = 我們人錄 #045 同一個人。
        南郡寫「南街第三進」是舊地址，北郡的「南街七進」是新地址。
        張正吉宣化二年五月搬的家。

組 2：萬通商號 vs 萬通泰昌 ── 確認同一家改名。
  證據：飛鴿驛六月十八日通報「萬通改名為萬通泰昌」。
        南郡的「萬通」紀錄是舊名，北郡的「萬通」也是舊名。
        北郡的「萬通泰昌」是新名。
        三筆紀錄背後是同一家。
```

OK。

**人工判斷確定**。

可以進**步驟三：選主筆**。

---

選主筆是這樣的：

```
組 1：
  C-007 順發（南郡） vs C-103 順發（北郡）
  哪一筆當「主筆」？

選的原則：
  資料最新的 = 北郡 C-103（地址是新的）
  關聯到最多 拍（deal）、事件（activity）、通籙的 = 兩邊都有但北郡多一些（新單）
  
結論：以 C-103 為主筆。
  C-007 被合併進 C-103。
  原 C-007 上的歷史 事件、通籙、拍 全部「重新指向 C-103」。
  C-007 標記為「已合併 → C-103」，本身不刪除。
```

尹知行特意規定 ── **原紀錄不硬刪**。

理由：

1. **歷史可回查**：未來如果有人問「南郡 C-007 那個編號是什麼」，能查得到「已合併到 C-103」。
2. **錯了能回滾**：如果之後發現「合錯了」，可以把 C-007 拆回來。
3. **審計留痕**：所有合併動作可追溯，誰合的、什麼時候合的、為什麼合的。

---

尹知行定的**合併欄位規則**：

```
合併時，每個欄位選一個值：

地址：選兩筆裡「最新一次更新」的那個
  C-007 寫「南街第三進」，C-103 寫「南街七進」
  最新更新的是 C-103 → 選 C-103 的「南街七進」

主營業務：兩筆同 → 用同的；不同 → 合併兩個（用逗號分隔）
  南郡萬通「多元」、北郡萬通「賣茶」 → 合成「多元、茶」

當家：選兩筆裡「最常被引用」的
  兩筆都是張正吉 → 沒爭議

慣用名（多值欄位）：合併兩邊的所有值
  C-007 慣用名：「順發」、「老順」
  C-103 慣用名：「順發商號」
  合併後：「順發」、「老順」、「順發商號」（去重）
```

每一筆合併動作，**都記錄在主筆紀錄底下**：

```
主筆 C-103 順發商號
合併歷史：
  [宣化二年九月一日] 從 C-007 合併
    來源：南郡分舵
    合併人：尹知行
    保留欄位：(無變更，C-103 較新)
    刪除欄位：(無)
    新增資訊：C-007 上的兩筆古老 事件 重新指向 C-103
```

未來任何人翻 C-103，**都看得到「這條紀錄怎麼變成現在這個樣子」**。

---

第二百四十天，尹知行實際做完三組合併。

合完之後，**全商會的人錄少了 12 筆、商號錄少了 7 筆**。

但每一筆「**少掉**」的，都還在原檔案夾的「**歷史紀錄區**」。**只是不再出現在主索引**。

尹知行翻整個商會的活躍紀錄。

**九千四百三十一筆 客身（contact）、兩千一百八十八家 商號（company）**。

但他知道 ── **這九千四百多筆裡面，至少還有幾百筆是重複的**。

他做的三組只是「**最明顯**」的。剩下的需要時間慢慢清。

---

第二百四十五天，蘇行又跑來。

「**尹副丞，我合錯了一筆**。」

尹知行翻紀錄。

```
昨日合併：
  C-201 「萬通布號」 合併到 C-145 「萬通泰昌」
```

蘇行說：「**我以為這兩家是同一家。但今天「萬通布號」的老闆來找，他說他跟「萬通泰昌」一點關係都沒有，剛好都叫萬通**。」

尹知行停下筆。

「⋯⋯**好**。」尹知行說，「**拆回來**。」

尹知行翻合併紀錄。

```
[昨日] C-201 → 合併到 C-145
  影響 事件：A-1199、A-1201、A-1204
  影響 拍：D-067
```

「**所有合併後重新指向 C-145 的 事件、拍、通籙 ── 全部改回 C-201**。」尹知行說，「**C-201 從『已合併』狀態恢復為「活躍」**。」

蘇行操作。

兩刻鐘後，**C-201 完全還原**。

尹知行那晚在《記事手冊》第九章加最後一條：

> **重契可以「逆」。**
>
> **這是為什麼我們從不硬刪**。

---

第二百五十天，東家來。

「**尹知行**。」屠東家說，「**我聽蘇行說，你合錯了一筆，又改回來了**。」

「⋯⋯是。」

「**前一個錄事司丞，三年前也合過一筆**。」屠東家說，「**他合完之後，原始紀錄被銷毀了。後來發現合錯了，改不回來。我們失去那家客戶**。」

尹知行沉默。

「**這是我為什麼今年初打了錄事司**。」屠東家說，「**不是因為他們算錯帳。是因為他們把錯誤當成終局**。」

「⋯⋯」

「**你的「重契」**。」屠東家說，「**留了一條退路。這比合得多準都重要**。」

尹知行抬頭。

「⋯⋯**東家**。」尹知行說，「**留退路有個成本 ── 倉庫要更大、查找會慢一點、儲存的紀錄量是兩倍**。**這個成本你願意付嗎**？」

屠東家想了一下。

「⋯⋯**付**。」他說，「**因為「能回頭」這件事，是這個商會最缺的東西**。」

尹知行行禮。

---

那晚尹知行翻第九章末尾。

他寫了一條總結：

> **去重（dedup） 的本質不是「找出重複」**。
>
> **是「在足夠的信心下合併、留下足夠的痕跡讓人可以回頭」**。
>
> 信心不夠 → 不合。
> 沒留痕跡 → 不合。
>
> 寧可保留「可能重複」的狀態，不要錯合。

第十章他要解決：屠東家每個月問「**今年下半年能收多少**」 ── 但**為什麼某個分舵的成交率特別低**？某類客戶**為什麼買比較多**？某個雜役**為什麼跟單卡得特別久**？

這些都需要**從堆積的資料裡看出規律**。

那是「**析數**」。



---

那夜尹知行在牆前盤膝坐下、閉目。

這一張新貼的紙條化作微光、沉入丹田。

胸口熱了一下、又涼了一下。

自此尹知行修為 ── **練氣中期・第九重「重契」**。

## 雜役筆記

*尹知行《記事手冊》第九章最後一頁。*

**▍Deduplication（去重 / 重契）**

CRM 最痛、最危險、最常出事的功能。尹知行穿越前死在這。

「**找出代表同一個實體的多筆紀錄，合併成一筆**」。

**▍為什麼必出事**

1. **同名不同人**（兩個馬青山）
2. **同人不同名**（張老闆 vs 張正吉 vs 張大爺）
3. **不可逆**：合錯了改不回來
4. **下游波及大**：一筆 contact 連著幾百條 activity、幾十筆 deal、幾條通籙 ── 合錯一筆 = 全部錯位

**▍正確流程的四步**

```
1. 標記可能重複（規則自動找候選）
2. 人工判斷（看更多 signal、確認）
3. 選 master record（主筆）
4. 合併欄位 + 重新指向 + 保留來源
```

**沒有任何一步該自動。** 自動只能「**提示**」、不能「**動手**」。

**▍Master Record（主筆）的選法**

合併時哪一筆當主：

- **最新更新**的那筆（資料新）
- **最多 deal/activity 關聯**的那筆（保留下游關係省力）
- **完整度最高**的那筆（欄位填得最齊）
- **手動指定**

**▍Survivor Rules（合併欄位規則）**

每個欄位怎麼選最終值：

```
Take Newest         選最近更新的
Take Most Complete  選最完整的（NULL 讓位給有值的）
Concatenate         合併兩個值（多值欄位）
Manual Pick         手動挑
Reject Conflicts    衝突時不合併、給人決定
```

不同欄位用不同規則。**地址用 Take Newest、Email 用 Concatenate（保留兩個）、姓名用 Manual Pick**。

**▍Fuzzy Match（模糊比對）**

不完全相同但相似。常用演算法：

- **Levenshtein distance**（編輯距離）：「萬通商號」vs「萬通商行」距離 1
- **Jaro-Winkler**：對「字首相同」加權，適合人名
- **Soundex / Metaphone**：發音相近（英文場景強）
- **Cosine similarity on embedding**：把姓名用 embedding 變向量比距離（RAG 那本書講的）

實務上**多 signal 加權**：

```
score = 0.4 × name_similarity 
      + 0.3 × email_match 
      + 0.2 × phone_match 
      + 0.1 × address_similarity

score > 0.85 → 自動標記候選
score > 0.95 → 高信心、提示優先合併
score < 0.5  → 確定不是同一筆
```

**▍永遠保留 audit trail（合併軌跡）**

每一次合併留紀錄：

```
merged_record:
  master_id: C-103
  merged_id: C-007
  merged_at: 2026-06-02
  merged_by: 尹知行
  field_choices: { address: "from C-103", main_business: "concatenated" }
  affected_records: [A-1023, A-1024, D-042, T-018]
```

**未來如果發現合錯了 → 照 audit trail 回滾**。

尹知行的「**重契可以逆**」靠的就是這個。

**▍Identity Resolution（身分識別）**

CRM dedup 在「**單一系統內**」。

**Identity Resolution** 是「**多系統合**」 ── 你的 CRM 裡的 contact、行銷工具的訂閱者、客服系統的工單發起人、Billing 的付款帳號 → 全部識別「**是不是同一個人**」。

工具：Twilio Segment、mParticle、Hightouch。**B2B SaaS 規模到一定程度幾乎必裝**。

**▍最後一句**

> 寧可不合，不要錯合。
>
> 信心不夠就保留「**可能重複**」狀態，**不要硬合**。

## 這一章你只要記得這三件事

1. **Dedup 從不該自動。** 系統提示「可能重複」、人工判斷、選 master、合併並留 audit trail。
2. **永遠保留來源紀錄。** 合併等於 soft merge、不是 delete。錯了能回滾才是專業。
3. **寧可不合，不要錯合。** 信心不夠的留「可能重複」狀態給下次處理。
