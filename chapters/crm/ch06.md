# 第 6 章　通籙

第一百三十五天。

陸瀚和錄事司四個雜役同時遇到一件事。

「**順發商號的張正吉**，**今天他兒子張仲安來說，他爹同時也是『**萬通商號**』的股東**。」蘇行報。

「**北街綢緞舖的劉萬山**，**今天說他現在還兼營『**南港鹽行**』的掌櫃**。」另一個雜役報。

「**裴遠分舵主送來消息**，**他發現西郡有三家商號的負責人，其實是同一個人**。」第三個雜役報。

陸瀚翻牆上的紙條。

他原本的設計：

```
Contact #045 張正吉 ── 所屬商號：#C-007 順發商號
Contact #128 劉萬山 ── 所屬商號：#C-019 北街綢緞舖
```

「所屬商號」**只能填一個**。

但現實是 ── **張正吉同時屬於順發、萬通**。**劉萬山同時屬於綢緞舖、南港鹽行**。

陸瀚的設計**不夠用了**。

---

那晚陸瀚坐在長案前。

他想了很久。

他在前世做過的所有 CRM 系統，**「一個 contact 屬於一家公司」是預設假設**。直到客戶告訴他「我們客戶有些是『**多家公司的負責人**』」 ── 他才發現預設錯了。

人和公司之間的關係，**從來就不是「一對多」，而是「多對多」**。

一個人可以同時為多家公司工作（董事、股東、顧問、兼職）。
一家公司可以有多個人（員工、董事會、外部顧問）。

兩邊都是「**多**」。

---

陸瀚開一個新的本子。

封面三個字：

**通籙**

「**通**」是「**互通**」、「**籙**」是「**記載關聯的冊子**」。

通籙不像人錄、商號錄、拍錄那樣記「實體」。它記的是 ── **實體和實體之間的關係**。

每一條通籙紀錄長這樣：

```
編號  T-001
人  Contact #045 張正吉
商號  Company #C-007 順發商號
角色  當家
起始日期  宣化二年一月一日
結束日期  （空白 = 進行中）

編號  T-002
人  Contact #045 張正吉
商號  Company #C-019 萬通商號
角色  股東
起始日期  宣化二年五月十日
結束日期  （空白）
```

兩條通籙紀錄。同一個 contact #045。指向兩個不同的 company。

張正吉**同時**屬於兩家商號。

陸瀚撕掉牆上原本「**所屬商號**」的單一欄位設計。

改成 ── **「所屬商號」欄位不存在於 contact，而存在於通籙**。

每筆通籙是一條「**這個人在這家商號扮演什麼角色、從什麼時候開始、到什麼時候結束**」的紀錄。

---

第一百三十八天，蘇行又跑來。

「陸副丞，**張正吉退出萬通商號股份了**。」

陸瀚翻通籙 T-002。

「**改紀錄**。」他說，「**結束日期填今天**。」

「⋯⋯**不是把整條刪掉**？」

「**不刪**。」陸瀚說，「**他過去確實是萬通股東。這是歷史**。**未來如果有人問「過去三個月誰是萬通的股東」，我們翻通籙，找「結束日期是空白或晚於三個月前」的紀錄，就能答**。」

「⋯⋯**所以歷史紀錄要保留**？」

「**保留**。」陸瀚說，「**通籙是「關係的時間軸」**。**現在誰跟誰有關係、過去誰跟誰有關係，都看通籙**。」

陸瀚加註：

```
T-002 [更新]
結束日期 ← 宣化二年六月十日
更新原因：張正吉退出萬通股份
更新人：蘇行
更新時間：今日
```

---

第一百四十天，裴遠又來總櫃。

「陸副丞。**我西郡發現的那三家商號**，**負責人是同一個人**。」

陸瀚抬頭。

「**人是誰**？」

「**他自報叫『鄭三郎』**。**但這個名字我們三家商號的紀錄都不一樣**。」

陸瀚翻人錄。

「**鄭三郎」、「鄭老闆」、「鄭三公子」 ── 三筆 contact 紀錄，分別屬於三家商號**。

陸瀚跟裴遠對細節：

```
鄭三郎  住中街  賣藥材
鄭老闆  住東街  賣布
鄭三公子 住西街  做仲介
```

裴遠說：「**這三個地址都對。中街是鄭三郎的住處、東街是「鄭家布行」的店面、西街是「三和仲介」的辦公處。三個都是同一個人**。」

陸瀚想了一下。

「**合併**。」他說，「**三筆 contact 紀錄，合併成一筆。但通籙保留三條，分別指向三家商號**。」

合併後：

```
Contact #312 鄭三郎（並稱：鄭老闆、鄭三公子）
慣用名：
  中街 → 鄭三郎
  東街 → 鄭老闆
  西街 → 鄭三公子

通籙：
  T-218 → 中州藥材行（角色：當家）
  T-219 → 鄭家布行（角色：當家）
  T-220 → 三和仲介（角色：當家）
```

一個 contact 紀錄、三條通籙、三個 company。

未來任何雜役聽到「鄭老闆來了」，搜「鄭老闆」 → 命中 Contact #312 → 透過通籙看到他屬於三家商號 → 雜役知道他不只是布行的人。

---

第一百四十四天，陸瀚發現**通籙的第二個用法**。

「**一筆 deal 涉及多個 contact**。」

例：D-023「萬通商號採購茶葉 1200 兩」。

談這筆 deal 的人不只一個：

- 張仲安（萬通商號的二掌櫃，主要對接人）
- 鄭三郎（萬通的股東，決定權）
- 孟元（萬通的會計，過手錢的人）

如果他在 D-023 的 deal 紀錄裡只填「主要聯絡人 = 張仲安」 ── 漏掉鄭三郎的決定權、漏掉孟元的付款窗口。

於是他建第二類通籙 ── **Deal × Contact 的通籙**：

```
編號  T-D023-1
Deal  D-023
人  Contact #047 張仲安
角色  主要對接人

編號  T-D023-2
Deal  D-023
人  Contact #312 鄭三郎
角色  決策者

編號  T-D023-3
Deal  D-023
人  Contact #X-孟元
角色  付款窗口
```

三條通籙，把 D-023 連到三個 contact，**各自記他們的角色**。

未來任何雜役看到 D-023，**翻通籙就知道「這筆 deal 涉及哪些人、各自扮演什麼角色」**。

跟對方談的時候，**知道該找誰、跟誰講什麼**。

---

第一百五十天，陸瀚的桌前出現了**五本書並排**：

```
《人錄》    Contact 實體
《商號錄》  Company 實體
《事錄》    Activity 實體
《拍錄》    Deal 實體
《通籙》    所有實體之間的關係
```

通籙裡有：

- Contact × Company（誰屬於哪家公司）
- Contact × Deal（誰參與了哪筆生意）
- Activity × Contact（這條 activity 涉及誰）
- Activity × Deal（這條 activity 涉及哪筆生意）
- Contact × Contact（誰是誰的親屬、介紹人）
- Company × Company（誰是誰的母公司、子公司、合資對象）

**只要兩個實體之間有關係，就在通籙開一條**。

---

陸瀚在《記事手冊》第六章寫：

```
五本書合在一起，回答任何客戶問題。

問：張正吉這個月跟我們聊過什麼？
步驟：
  人錄 → Contact #045 張正吉
  通籙 → 找 contact_id = 045 的所有 T-X
  事錄 → 找所有引用 T-X 的 activity
  按日期排序

問：順發商號今年下了多少單、收了多少錢？
步驟：
  商號錄 → Company #C-007 順發商號
  拍錄 → 找 company_id = C-007 的所有 deal
  分階段統計、加總已收款項

問：鄭三郎這個人，對我們商會有多大價值？
步驟：
  人錄 → Contact #312 鄭三郎
  通籙 → 找他屬於的所有商號（三家）
  拍錄 → 找這三家商號的所有 deal
  加總所有完結 deal 的金額
  = 鄭三郎對我們商會的總貢獻
```

每個問題都是 ── **從一本書出發，透過通籙跳到下一本書，再跳，再加總**。

陸瀚看著桌上五本書。

他想 ── 這就是「**關聯式資料庫**」的本質。

每一本書是一張表。
表跟表用編號互相指（foreign key）。
複雜的關係用通籙（junction table）。

兩百年前他做的這套，**結構和兩百年後 PostgreSQL 一模一樣**。

---

第一百五十五天，屠東家又下到錄事司。

「陸瀚。」他說，「**全商會現在用你這套的有南郡、北郡、西郡、東郡、總櫃。五個地方**。」

「⋯⋯是。」

「**今年下半年，每個分舵的拍錄漏斗都送到我桌上**。」屠東家說，「**我發現一件事**。」

陸瀚等。

「**南郡和北郡都有「順發商號」的紀錄**。」屠東家說，「**但兩個分舵記的順發商號編號不一樣 ── 南郡叫 C-007、北郡叫 C-103**。」

陸瀚閉了一下眼。

他知道問題出在哪。

**每個分舵各自編號**。同一個商號在不同分舵有不同編號。整個商會看 ── **同一個客戶被當成兩個**。

陸瀚穿越前死掉那單 ── **是同一個人被當成兩個**。

陸瀚這次在這個世界的真正考驗 ── **是同一個客戶被分成五個**。

問題不一樣，但**根源一樣**：

> **沒有跨系統的唯一識別**。

---

陸瀚抬頭。

「⋯⋯**東家**。」他說，「**這事，我下一章解決**。」

屠東家挑眉。

「⋯⋯**下一章是什麼**？」

陸瀚笑了一下。

「⋯⋯**我亂講**。」他說，「**我意思是，下個月一定處理**。」

## 雜役筆記

*陸瀚《記事手冊》第六章開頭。*

**▍Relationship（關係 / 關聯）**

CRM 的第五個基本概念。**實體之間的連接**。不是新 entity，是 entity 跟 entity 的橋樑。

**▍一對一 / 一對多 / 多對多**

| 類型 | 例子 | 實作 |
|---|---|---|
| **One-to-One** | 一筆 deal 對應一張契約 | foreign key 直接放在其中一張表 |
| **One-to-Many** | 一家公司有多個聯絡人 | foreign key 放在「多」那邊（contact 有 company_id） |
| **Many-to-Many** | 一個人在多家公司、一家公司有多個人 | **junction table（通籙）** |

**▍Junction Table（連接表 / 陸瀚的通籙）**

實體和實體之間「多對多」的標準作法。

```sql
CREATE TABLE contact_company_role (
  id           bigint primary key,
  contact_id   bigint references contacts(id),
  company_id   bigint references companies(id),
  role         text,
  start_date   date,
  end_date     date,
  is_primary   boolean
);
```

每一筆 junction table 紀錄是「**一條關係**」。**關係本身可以有自己的欄位**（角色、開始時間、結束時間、是否主要）。

**▍歷史保留 vs 硬刪除**

陸瀚對蘇行說「**不刪，加結束日期**」。

CRM 場景：**關係改變不應該刪除歷史紀錄**。原因：

- *回看歷史*：「**三個月前誰是萬通股東**」
- *分析趨勢*：「**鄭三郎這個人，過去兩年陸續加入過幾家公司**」
- *法律與審計*：「**這筆 deal 當時的決策者是誰**」

標準作法：所有「關係」都有 `start_date` 和 `end_date`，**改變時更新 end_date，不刪原本紀錄**。

技術上叫 **Slowly Changing Dimension Type 2**（SCD2），或 **temporal table**。

**▍Soft Delete（軟刪除）**

跟上面相關的概念。

```sql
ALTER TABLE contacts ADD COLUMN deleted_at timestamp;
-- 刪除時：UPDATE contacts SET deleted_at = NOW() WHERE id = ?
-- 查詢時：SELECT * FROM contacts WHERE deleted_at IS NULL
```

軟刪除讓你可以「**還原**」、「**回看歷史**」、「**做合規審計**」。CRM 場景幾乎**永不硬刪**。

**▍正規化（Normalization）**

陸瀚從第三章「引號令」就開始做的事。資料庫設計術語。

- *1NF*：每個欄位只放一個值（不放陣列、不放 CSV）
- *2NF*：每個非主鍵欄位完全依賴主鍵
- *3NF*：每個非主鍵欄位**只**依賴主鍵（不依賴其他欄位）

實務上 **3NF 是 OLTP（交易型）系統的標準**。CRM 是 OLTP。OLAP（分析型，如資料倉儲）才會反正規化提速。

**過度正規化的代價**：JOIN 太多 → 查詢慢、SQL 難寫。所以實務上會有些「**戰略性反正規化**」（例如把 contact 的 company_name 冗余存進 deal，加快 dashboard 查詢）。

**▍實體完整性（Referential Integrity）**

通籙裡引用 contact_id = 045，**這個 045 一定要在 contacts 表存在**。如果 contact 被刪了，通籙紀錄怎麼辦？

四個選項：

- *CASCADE*：contact 刪 → 自動刪所有引用它的通籙
- *RESTRICT*：contact 不能刪，除非沒有任何通籙引用
- *SET NULL*：contact 刪 → 通籙裡的 contact_id 改為 NULL
- *NO ACTION*：放手不管，會炸（不推薦）

CRM 場景**幾乎都用 RESTRICT 或 soft delete**。**永遠不要 CASCADE 刪客戶資料**（一不小心刪掉一個 contact，連帶所有 deal、activity 都消失，災難）。

## 這一章你只要記得這三件事

1. **多對多用 junction table（陸瀚的通籙）。** 一個人在多家公司、一家公司有多個人、一筆 deal 涉及多個人 ── 全部用 junction table。
2. **關係本身可以有自己的欄位。** 角色、起始時間、結束時間、是否主要。這些不是 contact 的屬性，也不是 company 的屬性，是「**關係的屬性**」。
3. **改變關係用 end_date，不要硬刪。** CRM 紀錄要保留歷史，未來查得回去。

下一章：陸瀚規定「**成交後三天寄謝函、三十天回訪**」。這種規則目前靠雜役記。要自動跑起來。**籙令**（workflow automation）登場。
