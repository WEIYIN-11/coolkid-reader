# 第 4 章　接驛

> *築基初期・第四重「接驛」*

第九十天，雲書司驛站開張滿二十天，尹知行統計了用量：

```
鹽鐵司：來牒 47 次，成 44 次
刑部：來牒 31 次，成 29 次
漕運司：來牒 2 次，成 0 次
```

漕運司兩次全失敗。

第一次，牒上沒寫案號，驛站照律退回。
第二次，補了案號，但探子把「取卷」的牒遞到了「問事」的窗口，又退。

然後漕運司就再也沒來過。

尹知行去漕運司問。對方的探子頭領兩手一攤：

「你那驛站，**規矩太多**。牒式三種、窗口三個、密級四等。我的探子在水上跑慣了，看見公示碑就頭暈。**他寧可划三天船回司裡翻自家卷宗**。」

---

尹知行回程的路上想明白了一件事。

他立驛的時候，把全部心思放在「**驛站這一端**」── 窗口怎麼開、牒怎麼驗、紀錄怎麼留。

他沒想過「**來的人那一端**」。

旅人第一次到驛站，要知道：驛站在哪、開不開、能做什麼、牒怎麼寫、回文怎麼讀、驛站突然關門了怎麼辦。

這些事，**不該每個探子自己摸索**。

該有一個角色，替探子把這些全包了。

---

他想起在雲書司教探子用工具的方法 ── 工具包裡每件工具都有「用法簽」。

但這次不一樣。工具是死的，驛站是**活的** ── 驛站的所能會擴充（刑部不是剛加了「查屍格」嗎）、驛站會關門維護、驛站會換牒式版本。

**用法簽是死的，驛站是活的，中間需要一個活人。**

他管這個角色叫「**驛使（client）**」。

---

第一百天，尹知行向各司發《接驛案》：

「凡要用驛站的司，**設一名驛使**。探子不直接跟驛站打交道 ── **探子找驛使，驛使對驛站**。」

驛使的職責四條：

```
一、初見禮（initialize）
    驛使第一次代表本司接上某驛站時，先互報三事：
      我是誰（司名、驛使憑印）
      我會說哪版牒式（通文式・幾版）
      你能做什麼（驛站回所能清單）
    三事對齊，才開始往來。版本對不上，當場說清，不要往來到一半才發現。

二、代遞代收
    探子要查東西，用本司的話告訴驛使。
    驛使翻成標準牒式、遞驛站、收回文、翻回本司的話。
    探子全程不需要懂牒式。

三、所能在心
    驛使記住每座驛站的所能清單。
    探子問「能不能查 X」，驛使當場答，不用跑一趟。
    驛站擴充所能，驛使更新清單。

四、斷驛應對
    驛站關門、回文逾時、牒被退 ── 驛使按例處理：
    重試三次、換時段、或回報探子「此路不通，建議改走 Y」。
    不能讓探子傻等。
```

---

漕運司第一個試。

他們挑了一個識字最多的老船工當驛使，跟著尹知行學了五天。

第一百一十天，漕運司探子在徐州查漕糧案，要調雲書司的卷宗。他用漕運司的行話跟驛使說：「幫我撈一下雲書司有沒有徐州這條線上的底。」

驛使翻成標準牒：「問事二：查案〔徐州／漕糧／近三年〕」。

遞牒、收文、翻譯回行話 ──「雲書司在卷四案，三件跟你的線對得上，卷宗號抄給你。」

探子從頭到尾沒看過一眼公示碑。

當月，漕運司來牒三十一次，成三十次。

---

第一百二十天，出了一件事，讓尹知行把「初見禮」從「建議」改成了「**死規**」。

刑部驛站（第二座驛站，照雲書司的樣子立的）升了牒式版本：回文裡的「案件摘要」從一段話改成了分欄格式。

刑部公示了，但鹽鐵司的驛使**沒更新**。

鹽鐵司探子收到的回文，在他眼裡變成了亂碼格式 ── 驛使照舊版規則去讀新版回文，把「案號欄」讀成了「人名欄」。

探子拿著錯的人名查了三天。

尹知行查完事故，在《接驛案》裡補了一條：

> 初見禮不是只行一次。

> **每次接驛，必先對版本**。版本不合，寧可不通，不可錯通。

> 錯的回文比沒有回文危險十倍 ── 沒有回文，探子知道自己不知道；錯的回文，探子**不知道自己不知道**。

---

那晚他在牆上貼紙條：

> 立驛是一半，接驛是另一半。

> 驛站管「能做什麼」，驛使管「怎麼用、用不上怎麼辦」。

> **每次往來，先對版本。錯通比不通危險十倍。**

---

那夜尹知行在牆前盤膝坐下、閉目。

這一張新貼的紙條化作微光、沉入丹田。

胸口熱了一下、又涼了一下。

自此尹知行修為 ── **築基初期・第四重「接驛」**。

## 雜役筆記

*尹知行《諸探之約》第四章。*

**▍MCP Client（驛使）**

AI 應用內負責跟一個 MCP server 對話的元件。一個 client 對一個 server（一個驛使盯一座驛站）。

職責對應：
- 建立連線、做 initialize 握手
- 把應用的需求轉成協議訊息（JSON-RPC）、把回應轉回應用格式
- 維護 server 的能力清單快取
- 處理連線錯誤、逾時、重試

**▍MCP Host（驛使的上司）**

承載多個 client 的應用本體（Claude Desktop、Cursor、Cline 等）。Host 管：使用者授權、多 server 的協調、安全策略。

```
Host（應用）
 ├─ Client A ↔ Server A（GitHub）
 ├─ Client B ↔ Server B（Slack）
 └─ Client C ↔ Server C（自家資料庫）
```

探子（LLM）活在 host 裡，永遠不直接碰 server ── 跟「探子找驛使、驛使對驛站」一個結構。

**▍Initialize Handshake（初見禮）**

MCP 連線的第一步，三樣資訊互換：

```
client → server: initialize 請求
  - protocolVersion（我會說哪版協議）
  - capabilities（我這端支援什麼）
  - clientInfo（我是誰）

server → client: initialize 回應
  - protocolVersion（協商後的版本）
  - capabilities（我提供什麼：tools? resources? prompts?）
  - serverInfo（我是誰）

client → server: initialized 通知（確認，開始正式往來）
```

**版本協商失敗就斷線** ──「寧可不通，不可錯通」。

**▍Version Skew（版本漂移）**

鹽鐵司事故的學名：通訊兩端對「格式長什麼樣」的理解不一致。

防範：
1. 每次連線都協商版本（不是第一次連線才做）
2. 格式變更走版本號，不悄悄改語義
3. 收到讀不懂的欄位：明確報錯，**不要猜**

「錯的回文比沒有回文危險十倍」── 靜默的格式錯誤會讓 agent 拿著錯誤資料繼續推理，錯誤被放大而不是被攔截。

**▍Abstraction Layer 的價值**

漕運司從「2 次全敗」到「31 次成 30 次」── 變的不是探子，是中間多了一層驛使。

把協議細節（牒式、窗口、密級、重試）封裝在 client 層，使用者（探子）只面對自己的語言。**採用率問題經常不是能力問題，是介面成本問題**。

**▍錯誤處理的層級**

驛使的「斷驛應對」：
- **可重試**（逾時、暫時關門）→ 自動重試 N 次、退避
- **不可重試**（牒式錯、密級不符）→ 立即回報，不要傻試
- **降級**（此路不通）→ 給替代方案，不要讓上游空等

## 這一章你只要記得這三件事

1. **Server 是一半，client 是另一半。** 互通失敗經常不是 server 不好，是接入成本太高 ── 漕運司寧可划三天船。Client 層把協議細節全包掉。
2. **Initialize 握手每次連線都做：版本、能力、身分三件套。** 版本對不上寧可斷線 ── 錯通比不通危險十倍。
3. **錯誤分三級處理：可重試的自動重試、不可重試的立即回報、不通的給替代路。** 不能讓上游傻等。

下一章：驛站多了，新問題出現 ── 同一份資料，有的驛站做成「取卷」、有的做成「問事」，探子用起來體驗天差地遠。三類驛件**什麼時候該用哪個**，要有設計準則。**譯語**。
