# 第 11 章　校盟

> *築基初期・第十一重「校盟」*

第三百六十天，驛盟司運轉快滿一年。

溫止把尹知行叫去，問了一個讓他答不上來的問題：

「朝廷要把驛盟推到**全境十三司、外加七個鄰邦盟友**。」

「推之前，我問你一句 ── **你怎麼知道它真的好了？**」

尹知行說：「這一年，揚州案那種事沒再發生，驛餉降了一半，五籬擋下兩次境外滲透⋯⋯」

「我問的不是『過去沒出事』。」溫止打斷他，「我問的是『**推到二十方之後，會不會出事**』。」

「過去沒出事，可能是**運氣**，可能是**規模還小**。」溫止說，「你怎麼證明，不是還沒輪到出事？」

尹知行答不上來。

---

他想起在雲書司的「試煉」── 用「已知答案的測試集」驗探子。

但那是**驗一個探子**。

現在要驗的是**整條驛路**：十三司的驛站、驛使、謀篇官、合議堂、起居注、五籬 ── 一個跨二十方、上百個環節的盟。

驗一個探子，是看它「答對幾題」。
驗整條盟，是看**所有環節串起來、在壓力下、會在哪裡斷**。

這是兩件事。

---

第三百七十天，尹知行設計了「**校盟三場**」。

不是真的辦案 ── 是**演習**。用假案子、假敵人，把整條驛路拉到極限，看它在哪斷。

```
第一場：串驛校（流程聯驗 / integration test）

  擬一個必須「十三司全參與」的大案（假案）。
  從立案 → 謀篇拆解 → 並行查 → 跨驛調料 → 合議 → 結案，
  整條走一遍。

  驗的不是某一司強不強 ── 是「交接處」漏不漏：
    甲司的產出，乙司接得住嗎？
    謀篇官畫的圖，執行得動嗎？
    合議堂的裁決，各司認嗎？

  單環節再強，交接處斷一個，整條盟就斷。
```

第一場串驛校，當場就斷了三處：

- 兵部驛站的回文格式，太僕寺驛使讀不順（版本漂移，第四章那個病又犯了，因為太僕寺新換了驛使沒對版本）。
- 謀篇官畫的圖裡，有一個任務同時依賴刑部和戶部，**兩司都以為對方先做**，又雙雙空等（第六章的病在新人身上重演）。
- 合議堂裁決後，鹽鐵司不認 ── 因為裁決的「監驛」是戶部出身，鹽鐵司覺得偏袒。

三處都不是「能力問題」，是「**接縫問題**」。尹知行一條條補：版本對齊納入驛使月考、依賴圖強制標「誰先」、監驛改由驛盟司中立指派。

---

```
第二場：壓驛校（壓力測試 / load test）

  同時發一百個案子，看驛路在洪峰下哪裡先垮。
```

壓驛校垮在一個誰都沒料到的地方 ── **不是驛站，是驛使**。

驛站書吏不夠可以加，但每司只有一個驛使，一百個案子湧來，驛使成了瓶頸，牒在他手上積成山。

尹知行的對治：驛使從「一司一人」改成「一司一班」，並設「**急務優先、慢務入隊**」（第九章慢驛分流的延伸）。洪峰下，急案照樣快、慢案排隊等 ── 不再一起卡死。

---

```
第三場：破驛校（混沌測試 / 紅隊 / chaos + red team）

  尹知行親自當「敵國」，專挑驛路最險的地方下手：
    － 半途關掉一座驛站，看依賴它的案子會不會連環崩。
    － 派假線人投毒（第十章的注入），看五籬擋不擋得住。
    － 偽造一個司的全套文書，看牒驗真破不破。
```

破驛校是三場裡尹知行最重視的 ── 因為前兩場驗「正常情況下順不順」，破驛校驗「**出事的時候塌不塌**」。

關驛站那一擊，暴露了一個大洞：刑部驛站一關，**七個依賴它的案子全卡死**，沒有任何退路。

尹知行補了「**斷驛備案**」：每座關鍵驛站，指定一個「次選來源」── 刑部驛站斷了，部分卷宗可改向大理寺驛站調（雖然慢、雖然不全，但案子不會整個死）。

> 一座驛站斷，不該帶塌一片。
> **每條依賴，都要有一條退路。**

---

校盟三場，前後跑了四十天，補了十九個洞。

第四百一十天，尹知行向溫止交校盟總卷。

溫止翻完，問最後一個問題：「十九個洞補完了。**還有沒有第二十個？**」

尹知行老實答：「一定還有。校盟校得出『我想得到的險』，校不出『我想不到的險』。」

「所以呢？」

「所以不能一次全推。」尹知行說，「**先開一方、再開一片、最後全開**。」

他呈上《開盟次第》：

```
先開一方（灰度 / canary）：
  只先讓「漕運司 ↔ 鹽鐵司」兩方按新盟全規運轉一個月。
  出事，只出在兩方之間，補了再擴。

再開一片（分批 / staged rollout）：
  穩了，加到十三司。再穩，才加鄰邦。

留一條退路（rollback）：
  每一步都備「退回上一步」之法。
  新盟若在某方崩，那方先退回舊制，不牽連全局。
```

「不要一次點全天下的燈。」尹知行說，「先點一盞，看它穩了，再用它去點下一盞。」

溫止在總卷上用了印。

這一次他多說了一句：「**這句話我聽過。**」

尹知行一愣。

「雲書司來的人說的。」溫止說，「『散燈』。」

---

那晚他在牆上貼紙條：

> 「過去沒出事」不等於「不會出事」── 可能只是還沒輪到。

> 校盟三場：串驛校接縫、壓驛校洪峰、破驛校塌方。

> 校得出想得到的險，校不出想不到的險 ── 所以**先開一方、再開一片、留一條退路**。

---

那夜尹知行在牆前盤膝坐下、閉目。

這一張新貼的紙條化作微光、沉入丹田。

胸口熱了一下、又涼了一下。

自此尹知行修為 ── **築基初期・第十一重「校盟」**。

## 雜役筆記

*尹知行《諸探之約》第十一章。*

**▍為什麼 multi-agent 系統特別難驗**

單 agent 驗的是「輸入→輸出」對不對（書 3 的試煉）。Multi-agent 系統的失效大多在**交接處與湧現行為**，不在單一節點：

- 單環節全部正確，串起來仍可能失敗（接縫、依賴、版本）
- 失敗是**非確定**的（LLM 有隨機性）、**規模相關**的（小規模不出、大規模才出）
- 「過去沒出事」常是樣本不足，不是真的穩

**▍Integration Testing for Flows（串驛校）**

驗端到端的流程，不是單元件：

```
- 給定一個跨多 agent 的任務
- 斷言每個交接點：上游產出 schema == 下游期望 schema
- 斷言最終結果正確
- 重點測「接縫」：版本相容、依賴解析、結論交接
```

三個真實接縫病（都在前面章節出現過，這裡集中複發）：版本漂移（ch4）、依賴雙等（ch6）、裁決不認（ch7）── integration test 的價值就是讓這些在演習中暴露，不在生產中暴露。

**▍Load / Stress Testing（壓驛校）**

並發壓力下找瓶頸。LLM 系統的瓶頸常在意外的地方：

- API rate limit（驛使成瓶頸）
- 佇列積壓、超時連鎖
- 成本在洪峰下線性爆炸
- 對策：限流、優先佇列（急務優先）、降級

**▍Chaos & Red Team（破驛校）**

- **Chaos engineering**：主動注入故障（關掉一個 server、注入延遲），驗系統的容錯與退路。暴露「單點故障帶塌一片」。
- **Red teaming**：主動攻擊（prompt injection、偽造、越權），驗安全防線（ch10 的五籬）在真實對抗下成不成立。**安全防線不紅隊驗過，等於沒驗**。

關鍵心態：前兩場驗「順不順」，破驛校驗「**塌不塌**」── failure path 比 happy path 更需要測。

**▍Eval：自動化的驗收**

演習要可重複、可回歸 ── 把校盟做成 **eval suite**：

- 固定的測試案例集（含正常案、邊界案、攻擊案）
- 每次系統改動後自動重跑（防回歸）
- 工具：DeepEval、Ragas（RAG 場景）、LangSmith eval、人工評估（human-in-the-loop eval）對主觀品質

「還有沒有第二十個洞」── eval 永遠不完備，但**回歸測試保證補過的洞不再裂開**。

**▍漸進式發布（開盟次第）**

承認「測不出所有險」之後的正確姿態 ── 不賭一次全推：

| 階段 | 做法 | 失敗影響 |
|---|---|---|
| **Canary（先開一方）** | 1-5% 流量/兩方 | 局部 |
| **Staged（再開一片）** | 逐批擴大 | 可控 |
| **Rollback（退路）** | 每步可退回 | 可恢復 |

「先點一盞燈，穩了再點下一盞」= canary deployment 的本質，也是 ch12 要展開的「散燈」在工程上的形。

## 這一章你只要記得這三件事

1. **Multi-agent 的失效在交接處與規模，不在單節點。** 「過去沒出事」常是樣本不足 ── 單環節全對、串起來仍會在接縫斷。
2. **三種驗收：串驛校（接縫）、壓驛校（洪峰瓶頸）、破驛校（chaos + red team 驗塌方）。** 安全防線不紅隊驗過等於沒驗；failure path 比 happy path 更要測。
3. **承認測不完，就漸進式發布。** Canary 先開一方 → staged 逐批擴 → 留 rollback 退路。把演習固化成 eval suite 防回歸。

下一章：校盟過了，朝廷要開盟天下。但戶部清吏司在最後關頭跳出來反對 ──「**憑什麼我們的驛站要給別司、給鄰邦白用？**」開盟前的最後一戰，不是技術，是人心。**開盟**。
