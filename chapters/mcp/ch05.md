# 第 5 章　譯語

> *築基初期・第五重「譯語」*

第一百三十天，天下已有五座驛站：雲書司、刑部、漕運司、鹽鐵司、太僕寺。

尹知行去巡了一圈，回來的路上臉色很難看。

五座驛站，**五種開窗口的邏輯**。

---

太僕寺（管馬政）的驛站最誇張。

他們把**所有東西**都做成了「問事（tools）」：

```
太僕寺驛站・所能公示
【問事】
  問事一：查馬籍
  問事二：查馬價
  問事三：查牧場
  問事四：查馬醫
  問事五：取馬政條例第一卷
  問事六：取馬政條例第二卷
  ⋯⋯
  問事二十九：取馬政條例第二十四卷
```

「取馬政條例第七卷」是一個「問事」？

尹知行問太僕寺的驛丞為什麼這樣開。

驛丞理直氣壯：「問事窗口最好做啊。**什麼都做成問事，省事**。」

結果就是：探子的驛使要在**二十九個問事**裡找東西。探子問驛使「太僕寺能查什麼」，驛使念了二十九條，探子聽到第十條就忘了第三條。

更糟的是 ── 探子在推步的時候，看著二十九個選項，**經常選錯**。「查馬價」和「取馬政條例第十二卷（內含官定馬價）」都能回答馬價問題，探子每次都要賭一把。

---

刑部的驛站正好相反。

他們把所有東西都做成了「取卷（resources）」：

```
刑部驛站・所能公示
【取卷】
  屍格庫：卷一至卷四千七百
  案宗庫：卷一至卷九千二百
  刑名條例：卷一至卷三百
```

一萬四千卷，全是取卷。

探子要查「滄州去年溺死案」，驛使只能回答：「刑部有一萬四千卷，**你要哪一卷？**」

探子怎麼會知道要哪一卷？

結果是探子為了找一件案子，連取四十卷，一卷一卷自己翻 ── **檢索的活全壓在探子身上**。這不就是書一藏經閣開篇的問題嗎？資料存在，不等於資料找得到。

---

尹知行回驛盟司，把五座驛站的公示碑抄在一面牆上，看了一個晚上。

問題清楚了：

**立驛的人，都在用「自己省事」的方式開窗口，沒人在想「來的探子怎麼用」。**

他提筆寫《譯語三問》── 每個要立驛的司，開窗口之前先答三個問題：

```
第一問：這東西是「料」還是「菜」？

  探子拿到之後要自己讀、自己比對、自己消化的 → 料 → 取卷（resource）
  探子要的是一個現成的答案或動作結果 → 菜 → 問事（tool）

  例：「滄州溺死案的屍格原文」是料 ── 探子要自己細讀疑點。
  例：「滄州去年溺死案有幾件」是菜 ── 一個數字，不需要原文。

第二問：誰來決定用它？

  探子在推步中自行判斷要不要用 → 問事（tool）
    ── 所以問事的「名」和「述」要寫到探子一看就知道何時該用。
  探子明確知道要哪一份 → 取卷（resource）
    ── 所以取卷要有「目錄」可查，不能叫人盲猜卷號。
  使用者（人）選一個套路開始幹活 → 領訣（prompt）

第三問：窗口會不會太多或太少？

  問事超過十個 → 探子選擇困難，合併或分站。
  取卷沒有目錄 → 探子大海撈針，先補目錄。
  一個問事什麼都能問 → 等於沒有約束，拆開。
```

---

第一百四十五天，他帶著《譯語三問》重訪太僕寺。

二十九個問事，按三問重整：

「取馬政條例第 N 卷」這二十四個 ── **是料不是菜**，改成取卷，另加一份目錄卷。
剩下五個問事，再問第三問：「查馬籍」「查馬價」「查牧場」「查馬醫」職責清楚，**留**。

二十九個窗口變成：**四個問事 + 一個取卷庫（帶目錄）**。

一個月後回訪，太僕寺驛丞報：探子選錯窗口的事，從每旬七八件降到**零**。

---

刑部那邊，尹知行加的是「**目錄與問事並行**」：

一萬四千卷取卷不動 ── 那是料，本來就該開。

但在取卷前面，加三個問事當「引路」：

```
問事一：尋案〔州府／案類／年份〕→ 回案件列表＋卷宗號
問事二：尋人〔姓名〕→ 回該人在卷案件＋卷宗號
問事三：尋格〔屍格特徵〕→ 回相符屍格卷宗號
```

探子先「問事」拿卷宗號，再「取卷」讀原文。

**先問路，再取料。**

刑部探子找一件案子的平均耗時，從四十卷亂翻，降到「一問一取」兩步。

---

第一百五十天，尹知行整理「領訣（prompts）」的用法 ── 五座驛站裡只有雲書司開了這個窗口，而且**沒人來領過**。

他去問了幾個探子為什麼。

回答出奇一致：「不知道有這東西。」「知道，但我自己會查案，要訣幹嘛？」

尹知行想了想，把領訣換了一個位置 ── **不放在驛站等人來領，改成驛使在「探子第一次接某類案子」時主動遞**：

「你第一次查私鹽案？雲書司有一份《私鹽案查辦十二步》，要不要先看？」

一個月後，領訣的使用次數從零變成每旬二十次。

他在本子上記：

> 料（取卷）等人來拿，菜（問事）等人來點 ── 都行。

> 但**食譜（領訣）不能等人來領** ── 不知道食譜存在的人，不會想到要找食譜。

> 食譜要在「對的時機」遞到手上。

---

那晚他在牆上貼紙條：

> 開窗口的人最容易犯的錯：**用自己省事的方式開，不用來人好用的方式開**。

> 譯語三問：是料還是菜？誰決定用？窗口會不會太多太少？

---

那夜尹知行在牆前盤膝坐下、閉目。

這一張新貼的紙條化作微光、沉入丹田。

胸口熱了一下、又涼了一下。

自此尹知行修為 ── **築基初期・第五重「譯語」**。

## 雜役筆記

*尹知行《諸探之約》第五章。*

**▍Tools vs Resources vs Prompts ── 設計分界**

MCP 三類能力最常見的設計錯誤，就是太僕寺和刑部的兩個極端：

| 反模式 | 症狀 | 後果 |
|---|---|---|
| **全做成 tools**（太僕寺） | 「取第 N 卷」也是 tool | 工具列表爆炸、模型選擇困難、選錯率高 |
| **全做成 resources**（刑部） | 沒有檢索入口 | 檢索成本全壓在模型上、context 塞爆 |

正確分界（譯語三問的對應）：

1. **內容性質**：原文/檔案/資料集（模型要自己消化）→ resource；動作/查詢/計算（要結果不要過程）→ tool
2. **控制權**：模型在推理中自主決定呼叫 → tool（所以 description 品質至關重要）；應用端明確指定讀哪份 → resource；使用者選用範本 → prompt
3. **數量紀律**：tools 過多（經驗值 >10-15 個）→ 模型選擇準確率下降，考慮合併或拆 server

**▍「先問路，再取料」模式**

大資料集的標準開法：**檢索型 tool + 內容型 resource 並行**。

```
tool:  search_cases(prefecture, type, year) → 回 case_id 列表
resource: case://{case_id} → 回該案全文
```

模型先用 tool 縮小範圍、拿到識別碼，再用 resource 取原文。避免「一萬四千卷你要哪一卷」。

**▍Tool 數量與選擇準確率**

模型面對的 tool 越多，挑錯的機率越高（尤其功能相近的 tool）。對策：

- **合併**：「查 A」「查 B」「查 C」格式相同 → 合成「查 X（type 參數）」
- **分站**：不相干的能力拆成多個 server，host 按需掛載
- **命名區隔**：名字和 description 要讓模型能明確區分（「查馬價」vs「取馬政條例（內含馬價）」就是壞區隔）

**▍Prompts 的觸發問題**

「領訣沒人領」是真實痛點：prompts 是**使用者主動選用**的能力，但使用者不知道它存在。

對策是把 prompt 的「曝光」做在對的時機 ── client/host 在偵測到「使用者第一次做某類任務」時主動建議。**Discoverability 是 prompt 設計的一半**。

**▍Provider 視角 vs Consumer 視角**

「用自己省事的方式開窗口」是所有 API 設計的萬年病：

- Provider 視角：我的資料長這樣，所以介面長這樣
- Consumer 視角：來的人要完成什麼任務，所以介面長這樣

MCP server 設計永遠用 consumer 視角 ── 跟書二「從業務員的位置看一遍系統再設計它」同一個道理，**對象從人換成了模型**。

## 這一章你只要記得這三件事

1. **三類能力的分界：料 → resource、菜 → tool、食譜 → prompt。** 全做成 tool 模型選擇困難，全做成 resource 檢索壓力全在模型 ── 兩個極端都是災難。
2. **大資料集用「先問路再取料」：檢索 tool + 內容 resource 並行。** 別讓模型在一萬四千卷裡盲猜卷號。
3. **用 consumer 視角開窗口，不用 provider 視角。** 「我的資料長這樣」不重要，「來的探子要完成什麼」才重要。
