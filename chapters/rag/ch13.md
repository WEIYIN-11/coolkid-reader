# 第 13 章　長軸

> *練氣初期・第十三重「長軸」*

第五十天，門外來了一個客人。

不是弟子。是一個穿著外門派長袍的老者，自稱「東岩」，腰間掛著一個長竹筒。

「我是雲海宗的記事使。」老者說，「這次來，是把我們宗門三百年的記事卷帶來，請藏經閣『讀完之後告訴我們：我們宗門有沒有人，曾經練過跟離火九轉訣類似的東西』。」

他抽出長竹筒。

竹筒裡是一卷紙。攤開來，**三十丈長**。

尹知行掃一眼，估算：三十萬字。

---

東岩走後，尹知行坐在卷軸前，發了一會呆。

按過去半年的工作流：
1. 拆卷軸（chunking）
2. 算氣味（embedding）
3. 上萬卷盤
4. 弟子來問問題就查

照這個流程，把三十萬字拆完、上盤、可查，**至少要兩週**。

東岩的需求只有一個。

兩週成本，一個問題答案。

太貴。

---

尹知行抬頭看著三十萬字的卷軸。

他在想另一個方向：**直接讀完**。

藏經閣這半年新請的判官裡，有一個叫陸鶴的，年紀大但記性出奇地好。他能一口氣讀完一萬字，記住所有細節。

如果讓陸鶴**直接讀完整卷三十萬字**，再讓他答東岩的那個問題 ── 不就一天的事？

尹知行去找陸鶴。

陸鶴看了看卷軸：「⋯⋯三十萬字，我得讀三天，中間不能停。」

「能記住嗎？」

「⋯⋯能。但⋯⋯」陸鶴猶豫了一下，「**中間段我記得會比較模糊**。我每次讀超過五萬字之後，第四到第八萬字那段，回想時是模糊的。」

尹知行愣了一下。

那是他前世學 long-context 的時候，最早讀到的那篇 paper 講的事情。

> Lost in the middle.

長 context 模型最不擅長記住「中間段」。開頭和結尾記得清楚，中間像被淘掉了。

人類也一樣。

---

尹知行做了三件事的對比實驗。

**實驗 A：傳統 RAG**
拆卷軸三天 + 上盤一天 + 問問題秒回。
總時間：四天。
但只答得了**單一問題**。要再問就要再查（這部分很快）。

**實驗 B：直接讓陸鶴讀完**
讀三天 + 答問題半天。
總時間：三天半。
答的是**任何問題**（在卷軸範圍內）。
但中間段問題答得不準。

**實驗 C：混合**
先粗拆卷軸，按章節分十段（不細拆）。
東岩的問題進來，用萬卷盤抓**最相關的三段**。
把這三段（約十萬字）整個給陸鶴讀，讓他答。
總時間：粗拆一天 + 抓段半天 + 陸鶴讀十萬字一天 + 答半天 = 三天。
答案品質：高（陸鶴讀的是「壓縮過的、相關的」內容，不會 lost in the middle）。

實驗 C 勝。

---

尹知行寫了第三十八張紙條：

> 全部讀完，等於沒讀完。
>
> 先撈相關段，再讀全。

他在前世聽過一句話：

> RAG 的死，從 long context 出現開始；RAG 的生，從 long context 出現開始。

當時他不懂。現在懂了。

長 context **不是 RAG 的對手**。長 context 是 RAG 的**搭檔**。

短問題、大量問題：RAG 把候選段撈出來、重判（reranker） 細排、丟給模型。
長綜合問題、跨章節對照：RAG 撈大段（不細拆）、丟給 long-context 模型整段讀。

兩個各自的優勢，組合起來最強。

---

第五十四天，東岩來取答案。

尹知行給了一個三段話的回覆：

「您卷軸中，第七卷『靈樞篇』有兩段提到『火脈引氣自湧泉而上』的修煉方法，與離火九轉訣第七節高度相關。」

「另外，第十二卷『丹道補遺』有半頁文字描述『火屬性築基初期之三抱法』，疑似與離火九轉訣 LH-001 同源。」

「除此之外，您卷軸三十萬字裡，無其他與離火九轉訣明顯關聯之段落。」

東岩看了三遍。

「⋯⋯這三段，是怎麼找出來的？」

「我們先把您卷軸粗略分段，用我們的索引方法挑出最可能相關的三段，再讓我們最會記事的判官完整讀完那三段。」

「⋯⋯所以你們沒有讀完整卷？」

「沒讀完整卷。」尹知行老實答，「整卷三十萬字，要兩週才能精細處理。我們只精細處理了被挑出來的三段。」

東岩沉默了一會。

「⋯⋯我服了。」他說，「我們宗門過去十年，每次問藏經閣，藏經閣都說『沒這方面記載』。原來你們從來沒『讀完』我們的記事卷。」

「⋯⋯」

「但這次你們不是『讀完才答』。」東岩說，「你們是『先挑、再讀』。**這比讀完還準**。」

東岩臨走前，朝尹知行行了個非常深的禮。

「我回去就把我們宗門的索引方法改了。」他說，「謝謝。」

---

那晚，尹知行貼第三十九張紙條：

> 不要為了「讀完」而讀完。

> 為了「答對」而讀。

阿土在旁邊看：「尹師兄，那如果客人問的問題，**真的需要『讀完全卷』**才能答呢？」

尹知行想了一下。

「兩種情況。」他說，「第一，**問題本身是跨整卷的綜合題**，比如『這卷的核心思想是什麼』── 這種要全讀。第二，**問題的答案『沒有在明顯相關的段落裡』**，可能藏在你想不到的地方 ── 這種也要全讀。」

「⋯⋯但全讀很貴。」

「對。」尹知行說，「所以你要**先問問題是哪一種**。十個問題裡，八個是『可以精挑』的，兩個是『必須全讀』的。**不要把兩個的成本攤到八個身上**。」

阿土點頭。

尹知行心裡想：這就是 cost-aware routing 的精神。便宜的問題走便宜的路，貴的問題走貴的路。



---

那夜尹知行在牆前盤膝坐下、閉目。

這一張新貼的紙條化作微光、沉入丹田。

胸口熱了一下、又涼了一下。

自此尹知行修為 ── **練氣初期・第十三重「長軸」**。

## 雜役筆記

*尹知行第三十八、三十九張紙條的內容整理。*

**▍Long-context Models（長上下文模型）**

能一次處理幾十萬到上百萬 token 的模型。代表：

- *Claude*：200K tokens（約 15 萬中文字）
- *Gemini 1.5/2.0*：1M–2M tokens
- *GPT-4o*：128K tokens

長到可以一次塞一整本書、一份完整的程式碼倉、一份合約全文。

**▍Lost in the Middle（中段遺失）**

長 context 模型最不擅長記住「中間段」的細節。論文：Liu et al., "Lost in the Middle"（2023）。

實證：把答案放在輸入的開頭或結尾，模型準確率 ~80%；放在中段，掉到 ~50%。

**▍Long-context 取代 RAG 了嗎？**

**沒有。** 三個理由：

1. **成本**：長 context 的計算是 N²（context 變兩倍，成本變四倍）。三十萬字全餵，每次幾美金；RAG 撈相關段餵，每次幾分錢。
2. **延遲**：長 context 一次推理要幾十秒到幾分鐘；RAG 撈段毫秒級。
3. **資料更新**：長 context 每次都要重新讀整本；RAG 只要更新對應的 chunk。

**▍Long-context + RAG 的正確姿勢**

```
Query
  │
  ▼
RAG（粗段、撈 3-5 個最相關的「大塊」）
  │  每塊可能是一章、一節、一段文件
  ▼
Long-context Model（讀完這幾塊，綜合回答）
```

優勢：
- **短問題**走 RAG 直接撈 chunk
- **綜合問題**走 RAG 撈大塊 + long-context 細讀
- **跨整本綜合**才用 pure long-context（極少）

**▍何時用 pure long-context（不靠 RAG）**

- 整份文件 < 50K tokens（一次塞得下）
- 問題本身是「總結整份」「找全份矛盾」這類無法靠 chunk 拼出的
- 不在乎成本和延遲（一次性研究、不上線）

**▍Cost-aware Routing（成本路由）**

不同類型的問題走不同的處理路徑。**簡單問題用便宜模型 + 短 context，複雜問題才用貴模型 + 長 context。** 尹知行對阿土說的就是這個。

實務上：

```python
def route(query):
    complexity = classify_complexity(query)  # 一個小模型判斷
    if complexity == "simple":
        return rag_short_pipeline(query)        # Haiku + 5 chunks
    elif complexity == "medium":
        return rag_rerank_pipeline(query)        # Sonnet + 20 chunks + reranker
    else:
        return rag_longcontext_pipeline(query)   # Sonnet + 5 大段 + long-context
```

成本可以降 5-10 倍，使用者體驗幾乎沒差。

## 這一章你只要記得這三件事

1. **Long-context 不是 RAG 的替代品，是搭檔。** RAG 撈相關大段、long-context 細讀，組合最強。
2. **Lost in the Middle 是真的。** 不要相信「我把所有東西塞進 context，模型自己會找」這種話。中間段會被遺漏。
3. **Cost-aware routing：簡單問題走便宜路徑，複雜問題才用貴的。** 不要把兩種問題的成本攤平。
