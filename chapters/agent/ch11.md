# 第 11 章　上場

> *練氣後期・第十一重「上場」*

第八百天。

朝廷的詔令下來了 ── **雲書司擴編**。

```
原額：92 個探子。
新額：920 個探子。
時限：六個月內到位。
```

尹知行把詔令放在桌上、盯著看了很久。

92 → 920。**十倍**。

過去八百天他建好的「**圓桌、訊息台、案卷櫃、心法錄、圈籠**」── **能撐 92 個探子**。

920 個 ── 全部會炸。

```
920 個探子每日簡報 = 訊息台貼不下。
920 個案卷 = 案卷櫃裝不下。
920 個探子的派遣決策 = 尹知行一個人決定不來。
工具發放、暗號驗證、結果整合 ── 全部會崩。
```

尹知行那天召集嚴司丞、所有副司丞、和五個老探子。

「**規模放大十倍**」**這件事**。」尹知行說，「**不是「**做十倍多的事**」**。**是「**整套運作方式要重做**」**。**」

---

尹知行那晚開始重新設計。

他列出**規模放大會炸的環節**：

```
1. 訊息台 ── 紙條太多沒人看得完
2. 尹知行一個人決策 ── 920 人的派遣他做不完
3. 工具發放 ── 需要更多後勤
4. 暗號表管理 ── 920 人共用 = 暗號保密度下降
5. 案卷儲存 ── 物理空間不夠
6. 訓練 ── 新探子上手快不起來
7. 即時監控 ── 哪個探子卡住、哪個出事、看不過來
8. 成本 ── 920 個探子的薪資、工具、簡報送遞費 = 十倍預算
```

八個環節、每個都要重做。

尹知行從哪裡開始？

---

**第一件事：分層**。

不再是「**尹知行一個人 + 920 個探子**」這種扁平結構。

而是：

```
[總督（尹知行）]
    │
[副督] × 10（每個負責 92 個探子）
    │
[探子] × 920
```

每個副督**就是過去 800 天的「**小尹知行**」**：
- 自己決定派誰去哪
- 自己看每日簡報
- 自己解小衝突
- 重大事項才上呈總督

尹知行自己只需要管 10 個副督，**不用管 920 個探子**。

「**人類管 7 ± 2 個下屬最有效**」 ── 尹知行前世讀過這個結論。雲書司套用這個結構。

---

**第二件事：訊息台分區**。

920 個探子不能共用一個訊息台。

分成 10 個區、每個副督一個區。每個區只放本區探子的簡報、副督每日看。

跨區的東西怎麼辦？

尹知行設計「**跨區公告**」 ── 每天黃昏，副督彙整本區當天「**對其他區可能有用的資訊**」**，貼到「**總台**」**。

每個副督每天瀏覽**總台**（量小、最多十條）。

```
細節在區、要點在總台。
副督看區、總督看總台。
```

---

**第三件事：標準化派遣**。

92 個探子的時候、每張任務令尹知行親手寫。

920 個探子的時候、不可能。

尹知行設計**任務令模板** + **派遣決策樹**：

```
案件進來：
  
  第 1 問：案件規模？
    小（單州、單項）→ 走「**標準探子流程**」、模板 A
    中（跨州 OR 多項）→ 走「**團隊流程**」、模板 B
    大（跨多州 + 多項）→ 走「**督員協作流程**」、模板 C
  
  第 2 問：風險等級？
    低（純查詢）→ 探子自決、Level 1-2 工具
    中（接觸機要）→ 副督批准、Level 3 工具
    高（涉及朝廷高官）→ 總督批准、Level 4 工具
  
  第 3 問：時間壓力？
    急（< 30 天）→ 派最有經驗的探子
    一般（30-90 天）→ 標準分配
    寬鬆（> 90 天）→ 可派新探子練手
```

副督照樹做決定 ── **95% 的案件不需要總督介入**。

剩下 5% 上呈、尹知行才管。

---

**第四件事：監控台**。

920 個探子 ── 尹知行不可能逐個看狀態。

尹知行設「**監控台**」 ── 一塊大牆、貼著 10 區的「**即時狀況**」：

```
區 1：在線 78、卡住 2、超期 1、出事 0
區 2：在線 81、卡住 3、超期 0、出事 0
區 3：⋯⋯
```

每天早晨、尹知行掃監控台 ── 30 秒看完。

**看「**異常**」**：
- 卡住 > 5
- 超期 > 0
- 出事 > 0

只查異常區。其他區放手。

---

**第五件事：成本控制**。

920 個探子的成本是 92 個的十倍嗎？

尹知行算了一下：**不只十倍**。是十二倍。

```
直接成本（薪資 × 920）：10 倍
間接成本（後勤 / 通訊 / 暗號管理）：12 倍
協調成本（副督 / 監控台）：15 倍
```

尹知行對策：

```
1. 不是所有任務都派最強的探子。
   ── 低風險、簡單任務派新探子做。
   ── 高風險、複雜任務派老探子做。
   ── 這叫「**成本路由**」**（cost routing）。

2. 自動化盡量多。
   ── 暗號表發放、簡報收件、案卷整理 ── 由錄事司助手做。
   ── 探子和副督只負責「**判斷**」**和「**決策**」**。

3. 監控閾值要設。
   ── 任何探子的任務超過預算（時間或金錢） 50% ── 自動上呈副督。
   ── 避免「**單一任務吃掉整月預算**」**。
```

---

**第六件事：故障處理**。

920 個探子裡、**永遠會有「**今天 5 個卡住、3 個超期、1 個失蹤**」**這種事。

尹知行設**故障處理流程**：

```
卡住（探子 > 7 日無進展）：
  副督介入、給指示。
  3 天仍卡 → 重派一名支援探子。

超期（任務超過預定期限 20%）：
  副督複查任務令是否「**本來就不可能**」**。
  若是 → 修正任務令、延期。
  若否 → 探子能力問題、評估是否更換。

失蹤（探子 > 14 日無回報且失去聯繫）：
  立即觸發圈籠檢核。
  派最近的探子前去確認狀況。
  若確認「**被反向滲透 / 死亡**」 ── 啟動應變流程。

出事（探子提交「**異常結論**」 ── 涉及加錢 / 完全清白 / 高官介入）：
  雙重複核、必要時調離。
```

每一條都寫清楚、副督照做。

不依賴「**尹知行臨機應變**」 ── 因為總督只有一個、副督有十個。

---

第九百天，雲書司**920 個探子全部到位**。

第一週、運作出現「**混亂期**」 ── 各區副督還不熟、流程跑卡。
第三週、流程順了。
第六週、平均每日有 **80% 探子在執行任務、其餘 20% 在訓練、回司、休整**。

完成率（B 組評估標準）：**89%**。

跟 92 個探子時的 95% 比、**降了 6 個百分點**。

尹知行可以接受。

「**規模 10 倍、完成率降 6%**」── 整體產出是 **10 × 0.89 / (1 × 0.95) ≈ 9.4 倍**。

接近 10 倍產出，**有十倍的人手**。

---

第一千天，朝廷又下詔令。

```
雲書司年度評鑑：
- 案件處理量：年增 9 倍
- 對錯比：89%（過去十年平均 37%）
- 朝廷收回不法所得：320 萬兩
- 監察重大弊端：178 件（過去十年總和 67 件）

賞銀 5000 兩。
御賜匾額「**監察天下**」**。
```

尹知行那天晚上、坐在已經改成大廳的圓桌前。

桌上不只是十個竹筒。是一座**模型**：

```
[總台]（即時監控板、跨區資訊）
   │
[副督 × 10]（區域決策、簡報彙整）
   │
[訊息分區 × 10]（920 個探子的日常）
   │
[共用：暗號表、工具庫、心法錄、規矩、流程模板]
```

整個雲書司、從一個人 + 92 個探子 ── 變成一個**運作系統**。

---

那晚尹知行在《探子手冊》第十一章末尾寫：

> **規模化**不是「**做更多**」 ── 是「**重組**」**。

> 92 個探子的方法 ≠ 920 個探子的方法。
> 920 個探子需要：分層、分區、標準化、自動化、監控、成本控制、故障處理。

> 七件事缺一件、規模化就崩。

下一章、是這本手冊的最後一章。尹知行要把這一千天的所有東西**整理、開源、傳承**。**收劍**。



---

那夜尹知行在牆前盤膝坐下、閉目。

這一張新貼的紙條化作微光、沉入丹田。

胸口熱了一下、又涼了一下。

自此尹知行修為 ── **練氣後期・第十一重「上場」**。

## 雜役筆記

*尹知行《探子手冊》第十一章 ── 規模化七件事。*

**▍Production Deployment（生產部署）**

agent 從 prototype 到「**真實上線、給真實使用者用**」**。99% 的 agent prototype 死在這一步**。

**▍規模化七大環節**

尹知行的設計、對應業界實踐：

| 尹知行的 | 業界術語 |
|---|---|
| 分層（總督 → 副督 → 探子） | **Hierarchical Agent Architecture** |
| 訊息台分區 | **Sharding / Partitioning** |
| 標準化派遣 + 決策樹 | **Routing Layer** |
| 監控台 | **Observability / Monitoring Dashboard** |
| 成本路由 | **Cost-aware Routing** |
| 自動化後勤 | **Workflow Automation** |
| 故障處理流程 | **Incident Response / Runbook** |

**▍Observability（可觀測性）**

尹知行的「**監控台**」**。

生產 agent 必須能即時看到：

```
- 哪些 agent 正在跑、正在做什麼
- 每個 agent 的 token 用量、cost
- 每個 agent 的延遲
- 每個 agent 的 success / failure
- Tool call 的成功率、失敗原因
- Memory 使用情況
- Guardrail 觸發次數
```

實作工具：

- **LangSmith**：LangChain 出品、整套 trace
- **Langfuse**：開源、可自架
- **Phoenix (Arize)**：開源、視覺化好
- **Helicone**：專注 LLM call 紀錄
- **W&B Weave**：跟 Weights & Biases 整合
- **Datadog LLM Observability**：企業級
- **OpenTelemetry GenAI**：標準化 trace 格式

**▍Cost Tracking（成本追蹤）**

尹知行算 92 → 920 是 12 倍成本。

LLM agent 場景：

```
- Token cost：input + output token × price per million
- Tool call cost：呼叫外部 API 的費用
- Compute cost：跑 agent 的 server / Lambda 費用
- Vector DB / Memory cost：儲存費用
```

**▍Cost-aware Routing（成本路由）**

尹知行的「**低風險任務派新探子**」**。

```python
def route(task):
    complexity = classify(task)
    if complexity == "simple":
        return Haiku()      # 便宜、快
    elif complexity == "medium":
        return Sonnet()     # 平衡
    else:
        return Opus()       # 最強、最貴
```

實務上常見：90% 流量走便宜模型、10% 走貴模型。

**▍Latency Optimization（延遲優化）**

長 ReAct loop 慢：每輪 LLM call 都要 1-5 秒。10 輪 = 10-50 秒。

對策：

1. **Streaming**：邊生成邊輸出、使用者不用等完整答案
2. **Parallel tool calls**：能並行的工具同時呼
3. **Caching**：prompt caching、tool result caching
4. **Smaller model for simple steps**：路由
5. **Speculative execution**：預先呼叫可能用到的工具
6. **Prompt compression**：縮短不必要的 context

**▍Rate Limiting & Quota（限流與配額）**

尹知行的「**任務超預算 50% 上呈**」**。

production agent 必設：

```
- Per-user rate limit（每使用者每分鐘 N 次）
- Per-task token budget（每任務最多 N token）
- Daily cost ceiling（每日預算上限）
- Concurrent agent limit（同時跑的 agent 數）
```

沒設這些 = 一個 bug / 一次惡意呼叫 = 帳單炸。

**▍Incident Response / Runbook（事故應變 / 處理手冊）**

尹知行的「**故障處理流程**」**。

production agent 必有：

```
- 卡住的 agent 怎麼處理（kill / restart / escalate）
- 失敗率超過閾值怎麼辦（rollback / page on-call）
- 成本超預算怎麼辦（freeze / sample）
- 安全事件怎麼辦（quarantine / notify security team）
```

**寫成文字、團隊每人都能執行**。

**▍Versioning & Rollback（版本管理 + 回滾）**

agent 每個改動（prompt、tool、model 換版本）都要：

- **版本標記**
- **A/B test 跑兩週**
- **可回滾**

任何「**直接上 prod**」**的改動 = 等災難**。

**▍Deployment Patterns（部署模式）**

| 模式 | 描述 |
|---|---|
| **Canary** | 1% 流量試新版、沒問題再放大 |
| **Blue-Green** | 兩個環境、瞬間切換 |
| **Shadow** | 新版跑、不回應使用者、只記錄比較 |
| **Feature Flag** | 用旗標控制誰能用新版 |

**▍SLOs（服務水準目標）**

定義「**這個 agent system 應該達到什麼水準**」：

```
- Success rate ≥ 95%
- p99 latency < 30s
- Cost per task < $0.50
- Safety violations < 0.1%
```

設了 SLO ── 才有客觀標準說「**這個 agent 可不可以上線**」**。

**▍最重要的一句**

> Prototype → Production 不是「**部署到 server**」**。

> 是「**重組整套運作方式**」**：分層、分區、路由、監控、成本控、故障處理、版本管理、SLO**。

> 跳過任一環 = 出事是時間問題。

## 這一章你只要記得這三件事

1. **規模化不是「做更多」，是「重組」。** 92 個 agent 的架構 ≠ 920 個的架構。
2. **七大環節：分層 / 分區 / 路由 / 監控 / 成本控 / 自動化 / 故障處理。** 缺一個就崩。
3. **Observability 是 production agent 的命。** 看不見 = 不知道為什麼出事、不知道怎麼修。
