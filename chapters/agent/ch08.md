# 第 8 章　群行

> *練氣後期・第八重「群行」*

第三百二十天，朝廷大內又下了一份大任務。

```
任務：朝廷有十州大旱、需要在三個月內完成「**十州糧倉緊急盤點**」**。
人力：雲書司全力。
期限：90 天。
```

尹知行把任務令攤在圓桌。

十州。**三個月**。需要的是「**十個探子並行、結果整合**」。

但這次的任務有個之前沒有的特點 ── **十個探子彼此的工作會交織**。

```
- 州 A 的糧倉跟州 B 的糧倉中間有「**漕運跨州**」紀錄 ── 兩個探子都會碰到
- 「**糧商**」在多個州都有分號 ── 三個探子可能同時接觸同一個商號
- 朝廷規定的「**標準糧倉量**」是中央定的 ── 十個探子用同一份標準
```

**並行不只是「**各做各的**」**。

是「**各做各的、但有重疊**」。

尹知行得設計「**他們怎麼互動**」。

---

尹知行那晚畫了一張圖：

```
                  [我（orchestrator）]
                          │
        ┌────┬────┬────┬────┬────┬────┬────┬────┬────┐
        ↓    ↓    ↓    ↓    ↓    ↓    ↓    ↓    ↓    ↓
       州 A  州 B  州 C  州 D  州 E  州 F  州 G  州 H  州 I  州 J
       探子  探子  探子  探子  探子  探子  探子  探子  探子  探子
        │    │    │    │    │    │    │    │    │    │
        └────┴────┴────┴────┴────┴────┴────┴────┴────┴────┘
                          │
                  [共用：標準糧倉量、跨州漕運紀錄、商號名錄]
```

中央一個我（orchestrator）。
十個探子（workers）。
中間有「**共用資源**」（shared state）。

尹知行把這個結構叫「**督**」「**員**」「**台**」：

- **督**：他自己。負責拆任務、分配、整合、解衝突。
- **員**：十個探子。各自跑自己的 推步（ReAct）。
- **台**：共用的「**訊息台**」**。所有探子寫進去的東西其他探子都看得到**。

---

「**訊息台**」是新東西。

尹知行在司門口設一個大公告欄，叫**訊息台**。

每個探子每天派人來貼簡報、看別的探子貼的。

格式統一：

```
[第 N 天 / 州 X]
我今天做了什麼：
  ⋯⋯
我今天發現了什麼（可能對其他探子有用）：
  ⋯⋯
我今天問什麼（需要其他人配合）：
  ⋯⋯
```

第三段是關鍵：**「**需要其他人配合**」**。

```
範例：
[第 7 天 / 州 C]
我發現：州 C 有大量「**漕運入糧**」公文。對方船號是「**永盛 12-17**」**。
我問：哪個州的探子也看到「**永盛 12-17**」這批船號？我們可以對照「**起運州 → 到達州**」**的數量**。
```

第二天，州 F 的探子看到，回了一條：

```
[第 8 天 / 州 F]
回應 #C 第 7 天：永盛 12-17 起運於州 F。我這邊紀錄起運 8000 石。
問州 C：你那邊抵達多少？
```

C 回：

```
[第 9 天 / 州 C]
回應 #F 第 8 天：抵達 6500 石。差 1500 石。漕運途中可能私售。
建議：兩位探子共同追查永盛 12-17 沿途停靠點。
```

「**訊息台**」**讓探子之間「**自動發現對方需要的資訊**」**。

不用尹知行中介。

---

第三百三十天，**訊息台運作十天之後**，尹知行發現一個問題。

**有兩個探子在搶同一個證人**。

```
[第 11 天 / 州 D] 我打算明天去拜訪糧商「**永富號**」**掌櫃**。
[第 11 天 / 州 G] 我打算明天去拜訪糧商「**永富號**」**州 G 分號掌櫃**。
```

兩個探子都要拜訪「**永富號**」。

永富號是個跨州的大商號。州 D 探子拜訪本部、州 G 探子拜訪分號。

**問題不是「**他們都拜訪**」**，是 ── 兩個探子可能讓對方「**起疑**」。

如果永富號的本部和分號互相通氣 ──「**昨天有外地人來訪、今天又有人來訪**」── 對方會警覺。

尹知行在訊息台貼公告：

```
[督令]
跨州商號（永富、永盛、永興等）的訪查、由我統一安排時間。
任何探子要訪此類商號、先在訊息台告知、督核准後再行動。
```

從那天起，訊息台多了一條規則 ── 「**督令**」：尹知行自己貼的、所有探子必須遵守的。

---

第三百四十天，**第二個問題**。

兩個探子的結論**互相打架**。

```
[州 B 結論]：跨州漕運私售在「**起運州**」端舞弊。
[州 J 結論]：跨州漕運私售在「**抵達州**」端舞弊。
```

兩個都言之鑿鑿。

尹知行召兩個探子回司、面對面討論。

州 B 的探子拿出「**起運州的單據**」── 確實有改動痕跡。
州 J 的探子拿出「**抵達州的入庫量**」── 也有不符。

兩個都對 ── **同一筆漕運，**兩端都被動了手腳**。

「**起運州虛報船運出量、抵達州虛報實際入庫量、中間私售」 ── **三端一起串供**。

#B 和 #J 兩個探子的結論「**互相打架**」 ── 但結合起來，是**比兩個結論單獨都重要的真相**。

尹知行把這個叫「**辯論**」（debate）。

```
[督令]
凡兩位探子結論看似衝突 ── 不要急著選一個。
召兩位面對面、把證據攤開、看是否「**兩個都對、合起來是另一件事**」**。
```

---

第三百五十天，**第三個問題** ── 探子之間有「**搶功勞**」**的傾向**。

州 C 的探子發現「**永盛 12-17**」**漕運私售**。
州 F 的探子配合查到「**起運側資訊**」。

兩個合作完成。

但回司之後，**州 C 的探子報告中只寫自己的功勞**、**沒提州 F 的協助**。

州 F 知道之後不爽。

尹知行在訊息台加：

```
[督令]
結案報告必須列出「**收到哪些人幫助、給過哪些人幫助**」**。
個人功勞 = 自己做的 + 給別人提供的協助。
不可隱瞞他人貢獻。
```

從此每份結案報告末尾都有「**協作明細**」一段。

---

第三百六十天，**尹知行自己做一件事** ── **他不再「**指揮所有探子**」**。

過去 80 天，他每天看 10 份簡報、回 10 封信、解 N 個衝突。

他發現：**他自己變成 bottleneck**。

探子需要等他批准 ── 一兩天的延遲。
結論衝突等他面談 ── 三五天的延遲。

尹知行決定**部分授權**。

```
新規矩：
  - 簡單事務（拜訪一般商號、調用基本工具）→ 探子自決
  - 中等事務（跨州拜訪、調用高階工具）→ 主動發到訊息台、24 小時無異議 = 默認通過
  - 重大事務（接觸朝廷官員、調用 Level 3+ 工具）→ 督批准
```

「**24 小時無異議默認通過**」是新的。

尹知行從「**每件事都要批**」變成「**只批重大事**」。**探子們的執行速度上升 40%**。

---

那晚尹知行在《探子手冊》第八章末尾寫：

> **群行的四個基本動作**：

> 1. **通報**（broadcast）：自己做了什麼、發現了什麼，貼到訊息台讓所有人看。
> 2. **協作**（cooperation）：發現對方需要的資訊、主動提供。
> 3. **辯論**（debate）：結論衝突時面對面查、不要急著選邊。
> 4. **授權**（delegation）：督不該管所有事、抓重點就行。

> **多探子並行的關鍵不是「**怎麼派**」**。
> **是「**讓他們之間能彼此說話**」**。

下一章他要處理：探子有了任務、工具、推步、記憶、內省、群行。但 ── **如果某個探子被反向滲透（17 號那種被搶銀子的）**、**他自己變成「**為敵效力的探子**」**怎麼辦？**那是「**圈籠**」**。



---

那夜尹知行在牆前盤膝坐下、閉目。

這一張新貼的紙條化作微光、沉入丹田。

胸口熱了一下、又涼了一下。

自此尹知行修為 ── **練氣後期・第八重「群行」**。

## 雜役筆記

*尹知行《探子手冊》第八章的「群行四動作」。*

**▍Multi-Agent System（多 agent 系統）**

不是一個 agent、是**多個 agent 協作**完成更大的任務。

**▍常見的 multi-agent 架構**

**A. Supervisor-Worker（督員）**
尹知行的 orchestrator + 10 個探子。

```
      Supervisor
       /  |  \
   Worker Worker Worker
```

Supervisor 拆任務、分配、整合。
Worker 各自跑 ReAct、回報結果。

**B. Hierarchical（多層）**
Worker 自己再是 supervisor、底下有 sub-worker。

```
       CEO Agent
        /     \
    Manager   Manager
     /  \     /  \
   W1  W2   W3  W4
```

**C. Debate（辯論）**
兩個或多個 agent 對同一個問題**獨立回答**、然後互相批判、最後一個 judge agent 整合。

```
Agent A 答 X → Agent B 批判 A → A 改 → B 再批 → ⋯⋯ → Judge 結案
```

**D. Round-Robin（輪流）**
agents 圍成一圈、輪流發言（像會議）。每個 agent 看前面所有人的發言。

**E. Market / Auction（市場）**
任務丟出來、各 agent 競標、最便宜或最快的得標。

**F. Swarm（蜂群）**
大量同質 agent 各自探索、最終 consensus。常用於 search 場景。

**▍尹知行用的就是 Supervisor + 訊息台（shared state）**

加上：
- Broadcast（訊息台公告）
- Debate（衝突時面對面）
- Delegation（部分授權，督不管小事）

**▍Shared State / Blackboard（共享狀態 / 黑板）**

尹知行的「**訊息台**」**。

讓所有 agent 看得到、寫得到同一個地方。Pattern 來自 AI 早期的 Blackboard System（1970s）。

實作：
- 一個共用資料庫（PostgreSQL、Redis）
- 一個訊息匯流（Kafka、Pub-Sub）
- 一個共用文件（LangGraph 的 state、CrewAI 的 context）

**▍Agent Communication 的鐵則**

1. **Structured messages**（結構化訊息）：別讓 agent 用自然語言交流，用 JSON
2. **Explicit roles**（明確角色）：每個 agent 知道自己是誰、別人是誰
3. **Timeout & retry**（超時與重試）：一個 agent 卡住不能拖住整體
4. **Conflict resolution**（衝突解決）：明確的決策機制（投票、supervisor 決定、debate）
5. **Cost tracking**（成本追蹤）：每個 agent 消耗多少 token、別讓總成本失控

**▍實務框架**

| 框架 | 特色 |
|---|---|
| **LangGraph** | 把 multi-agent 畫成 DAG/state graph |
| **CrewAI** | 角色驅動（Manager / Researcher / Writer），簡單明瞭 |
| **AutoGen** | 微軟出品，conversation-based，最先進的 group chat 模式 |
| **Anthropic Subagents (Claude Code)** | spawn 子 agent 跑子任務、整合回主 agent |
| **DSPy** | 編譯式、可優化 |
| **Letta** | 帶 memory 的 multi-agent |

**▍Multi-Agent 的常見失敗**

1. **Coordination overhead**（協調成本）：agents 之間的通信成本 > 完成任務的成本
2. **Echo chamber**（迴音室）：所有 agent 互相同意、沒人提反對意見
3. **Lost in the relay**（傳話遊戲）：訊息經過多個 agent 變形、變質
4. **Diffusion of responsibility**（責任稀釋）：沒人覺得「**這事該我負責**」
5. **Token explosion**（token 爆炸）：N 個 agent 互相說話 = N² 成本

**▍何時用 single-agent vs multi-agent**

| 場景 | 用 |
|---|---|
| 單一目標、單一領域 | Single |
| 步驟 < 20、context 撐得住 | Single |
| 多領域、多技能 | Multi |
| 需要並行加速 | Multi |
| 需要互相驗證（debate） | Multi |
| 高度不可逆動作 | **Single + 人工**（不要交給 multi-agent） |

**業界 2025 共識**：

> **「**先做好 single-agent。**multi-agent 是最後選項，不是預設**」**。

> 因為 multi-agent 帶來的協調複雜度、debug 難度、成本，**遠超過你想像**。

**▍最重要的一句**

> Multi-agent 不是「**很多個 agent**」**。

> 是「**多個 agent 之間能彼此通信、協作、解衝突**」**。

> 訊息台 + 督員 + 辯論 + 授權 ── 四個動作做齊了，才算 multi-agent system。

## 這一章你只要記得這三件事

1. **Multi-agent 的本質是 communication，不是「多個 agent」。** 訊息台（shared state）+ 結構化訊息是關鍵。
2. **督員模式（supervisor + workers）是最常見起點。** 別一開始就玩 swarm 或 debate。
3. **Single-agent 永遠是首選，multi-agent 是最後選項。** 協調成本你會低估。
